# 캡스톤 — 흩어진 샘플을 "취업용 프로젝트" 하나로

지금까지 만든 것들(자기소개서 CRUD, JPA, React 분리, Spring Security, 테스트)은
각각 **"기능 조각"** 입니다. 취업 시장에서 통하는 것은 조각이 아니라,
**"문제를 풀어낸 깊은 서비스 하나"** 입니다. 이 모듈은 그 조각들을 **한 개의 포트폴리오 프로젝트로 통합**하는 방법을 안내합니다.

> 💡 **왜 통합인가?** 채용 조사 결론: 신입 포트폴리오는 **프로젝트 개수(5개+)가 아니라 깊은 2~3개**가 유리하고,
> **단순 CRUD 완성은 변별력이 없으며**, 승부처는 **"문제 → 과정 → 해결 → 정량적 결과 + 실제 배포 URL"** 입니다.
> (근거: [99_참고자료/신입개발자_취업준비_로드맵](../../99_참고자료/01_온보딩_취업/신입개발자_취업준비_로드맵_인턴초급개발자.pdf), [채용공고_비교분석](../../99_참고자료/01_온보딩_취업/채용공고_비교분석_공공SI서비스_인턴초급개발자.pdf))

이 문서는 **코드가 아니라 "설계도 + 실행 순서"** 입니다. 이미 가진 샘플을 재료로 쓰세요.

---

## 0. 완성 목표 (한 문장)

> **"실행되는 배포 URL을 가진, 성능 개선 수치와 트러블슈팅 기록이 있는 CRUD + 인증 서비스"**

주제는 자유입니다. 익숙한 **자기소개서/게시판**을 확장해도 좋고, 관심 도메인(중고거래·모임·가계부 등)으로 바꿔도 좋습니다.
중요한 건 주제가 아니라 **"무엇을 어떻게 개선했는가"** 입니다.

## 2. 단계별 로드맵 (각 단계마다 "증거"를 남겨라)

각 단계의 **산출물(증거)** 이 나중에 포트폴리오의 핵심 재료가 됩니다. **커밋·이슈·README에 기록**하세요.

### 1단계 · 통합과 도메인 확장
- 작업: CRUD 앱에 **회원 개념**을 붙입니다. "글쓴이 = 로그인한 사용자", "본인 글만 수정/삭제" 같은 규칙을 추가.
- 재료: Security 샘플의 인증 + Database 샘플의 CRUD.
- **증거**: 요구사항 정의(간단한 사용자 스토리 5~10개), ERD(README에 첨부).

### 2단계 · 성능 개선 스토리 ⭐ (가장 강력한 차별점)
- 작업 순서:
  1. MySQL에 **더미 데이터 10만~100만 건** 적재(스크립트/`GENERATE`/반복 INSERT).
  2. 느린 목록/검색 쿼리를 **`EXPLAIN`** 으로 분석 → 풀스캔 여부 확인.
  3. **인덱스 추가**, **N+1 문제 해결**(JPA `fetch join` 또는 `@EntityGraph`), **페이징** 개선.
  4. 개선 전/후를 **숫자로 측정**.
- **증거(핵심)**: `조회 응답 2.1초 → 90ms`, `DB CPU 70% → 15%` 처럼 **before/after 수치**.
  > 나쁜 예: "성능을 개선했습니다" / 좋은 예: "목록 조회가 인덱스 부재로 풀스캔(2.1초)이라, `created_at` 인덱스 추가로 90ms로 단축"

### 3단계 · 인증을 "기술 선택 근거"로 만들기
- 작업: 세션 / JWT / 리프레시 중 **하나를 선택**하고, **왜 그것을 골랐는지** 근거를 정리.
- **증거**: "화면을 서버가 그리므로 세션 선택" 또는 "앱/외부 연동 대비 JWT + 리프레시로 탈취 대응" 같은 **의사결정 서술**.
  (면접 단골 질문 — [Security 04 비교 문서](../Security/04_세션_vs_JWT_비교.md) 활용)

### 4단계 · 테스트로 품질 증명
- 작업: 핵심 비즈니스 로직 **단위 테스트** + 주요 API **통합 테스트**. ([Testing 모듈](../Testing/) 그대로 적용)
- **증거**: 테스트 개수, "왜 이 부분을 테스트했는가" 한 줄 설명. (커버리지 숫자보다 의도)

### 5단계 · 실제 배포 (돌아가는 URL) ⭐
- 작업: Docker로 컨테이너화 → **AWS EC2 + RDS(MySQL)** 배포 → 접속 가능한 데모 URL. `GitHub Actions`로 자동 배포.
- 재료: [Deploy 모듈](../Deploy/) (Dockerfile · docker-compose · CI/CD 워크플로 · AWS 가이드).
- **증거**: 데모 URL, 아키텍처 그림, "배포 수동 30분 → 자동 5분" 같은 개선 수치.

### 6단계 · 문서화 (README가 포트폴리오다)
- 작업: 아래 템플릿으로 README 작성. **설계도는 README에**, 본문은 **"개선 사례"에 집중**.
- **증거**: 잘 정리된 README + 의미 있는 커밋 메시지 + 트러블슈팅 기록.

## 3. README 템플릿 (그대로 복사해서 채우기)

```markdown
# 프로젝트명 — 한 줄 소개

## 1. 개요
- 무엇을 하는 서비스인가 / 왜 만들었나 (해결하려는 문제)
- 데모 URL: http://... (배포했다면 필수!)
- 기술 스택: Java 17, Spring Boot, JPA, MySQL, React, Docker ...

## 2. 주요 기능
- 회원가입/로그인, 글 CRUD, 검색/페이징 ...

## 3. 아키텍처 · ERD
- (그림) 프론트 ↔ API ↔ DB 구조, 테이블 관계

## 4. 문제 해결 사례 (핵심!)
### 4-1. 목록 조회 성능 개선
- 문제: 데이터 10만 건에서 목록 조회 2.1초
- 원인: created_at 정렬 컬럼에 인덱스 없음 → 풀스캔 (EXPLAIN 첨부)
- 해결: 인덱스 추가 + 커버링 인덱스
- 결과: **2.1초 → 90ms** (95% 단축)
### 4-2. N+1 문제 해결
- 문제 → 원인 → 해결(fetch join) → 결과

## 5. 기술 선택 근거
- 왜 JWT를 썼는가 / 왜 이 DB인가 (나열이 아니라 "이유")

## 6. 테스트
- 단위/통합 테스트 N개, 무엇을 검증하는지

## 7. 회고
- 아쉬운 점, 다음에 개선할 것
```

## 4. 트러블슈팅 기록 템플릿 (GitHub Issue/커밋에 남기기)

```
[문제]  로그인 후 새로고침하면 인증이 풀림
[상황]  JWT를 메모리에 저장 → 새로고침 시 소실
[시도]  localStorage 저장으로 변경, 만료 시 리프레시 토큰으로 재발급
[결과]  새로고침해도 로그인 유지, 액세스 토큰 만료(60초)도 자동 갱신 확인
[배움]  토큰 저장 위치의 트레이드오프(XSS vs 편의)를 이해함
```
> 이런 기록이 **"결과물"보다 값진 "사고 과정"의 증거**입니다. 채용담당자는 이걸 봅니다.

## 5. 흔한 실수 (피하기)

- ❌ ERD·아키텍처 그림만 잔뜩 → ⭕ 설계도는 README에, 본문은 **개선 사례** 중심
- ❌ 팀플에서 **내가 안 만든 부분까지** 기재 → ⭕ **본인 담당 모듈만** (면접에서 막히면 신뢰도 급락)
- ❌ 프로젝트 개수로 승부(5개+) → ⭕ **깊은 2~3개**, 개당 1~2페이지
- ❌ "성능 2배 개선" (막연) → ⭕ **"2.1초 → 90ms" (측정값)**

## 6. 완성 체크리스트

- [ ] 접속 가능한 **배포 URL** 이 있다
