# 06. 안전하게 쓰기 — 보안·법규·면접

> 🎯 목표: AI 도구에 **넣으면 안 되는 정보**를 구분하고, AI 결과물의 **저작권·라이선스·개인정보** 문제와 **AI 기본법**의 기본 내용을 알며, 면접에서 AI 관련 질문에 자기 생각으로 답할 수 있다.

> ⚖️ **이 문서는 법률 자문이 아닙니다.** 2026년 11월 기준으로 공개된 정부 발표와 언론 보도를 정리한 교육 자료입니다. 실제 업무 판단은 **회사의 보안 정책, 법무·개인정보 담당자**에게 확인하세요. 법령 세부(시행령, 과태료 기준, 계도기간 종료 시점)는 [국가법령정보센터](https://www.law.go.kr/) 원문으로 확인해야 합니다.

## 도입

AI 관련 사고는 대부분 **기술이 아니라 습관**에서 납니다.
"잠깐 에러만 물어보려고 했는데 로그에 고객 주민번호가 있었다", "급해서 개인 계정 챗봇에 사내 코드를 붙여 넣었다" 같은 일입니다.
2023년에는 국내 대기업 직원들이 사내 소스코드를 외부 챗봇에 입력한 사고가 보도되면서, 많은 회사가 AI 사용 규칙을 만들기 시작했습니다.

## 1. AI 도구에 넣으면 안 되는 것

**회사가 승인한 도구가 아니라면** 아래 정보는 넣지 않습니다. 승인된 도구라도 **필요 최소한**만 넣습니다.

| 우선순위 | 정보 | 예 | 대신 이렇게 |
|---|---|---|---|
| 🔴 1 | **비밀번호·API 키·토큰·인증서** | `application.yml`의 DB 비밀번호, JWT 시크릿 | `****`로 지우고 질문 |
| 🔴 2 | **개인정보** | 이름+전화번호, 주민등록번호, 주소, 이메일이 담긴 로그·DB 덤프 | 가짜 데이터(`홍길동`, `010-0000-0000`)로 바꿔서 |
| 🔴 3 | **고객사·기관의 내부 정보** | 공공기관 내부 시스템 구조, 미공개 사업 정보, 계약서 | 일반화해서 질문 ("A 기관" → "어떤 웹시스템") |
| 🟠 4 | **사내 소스코드 전체** | 프로젝트 폴더 통째로 | 문제 되는 **부분만**, 식별 정보 지우고. 사내 승인 도구 사용 |
| 🟠 5 | **내부 IP·서버명·접속 경로** | `10.x.x.x`, 내부 도메인, 관리자 URL | `<DB_HOST>` 같은 자리표시자로 |

> 💡 **"조합하면 특정되는 정보"도 조심하세요.** 이름을 지웠어도 "○○구청 민원팀 3년차, 2026년 3월 입사"처럼 여러 정보를 합치면 누군지 알 수 있습니다.

### 왜 위험한가

- 서비스 약관에 따라 입력이 **저장되거나, 사람이 검토하거나, 모델 학습에 쓰일 수 있습니다.** (기업용 요금제는 학습에 쓰지 않는다고 약정하는 경우가 많지만, **그 약정이 있는 계정인지** 확인해야 합니다.)
- 한번 외부로 나간 데이터는 **회수할 수 없습니다.**
- 공공·SI 프로젝트는 고객 기관의 보안 규정이 회사 규정보다 엄격한 경우가 많습니다. 망분리 환경에서는 외부 AI 서비스 접속 자체가 금지일 수 있습니다.

### 공공 분야 가이드 (참고)

| 문서 | 대상 | 비고 |
|---|---|---|
| 국가정보원 「챗GPT 등 생성형 AI 활용 보안 가이드라인」(2023-06) 및 이후 개정 가이드북 | **공공기관** | 개정판은 에이전틱 AI까지 다룬다고 보도됨. 원문은 국정원 홈페이지 확인 |
| 개인정보보호위원회 「생성형 AI 개발·활용을 위한 개인정보 처리 안내서」(2025-08) | AI를 **개발·활용하는 사업자** | 기획 단계부터 개인정보 보호를 넣으라는 내용 |
| 개인정보보호위원회 「생성형 AI 서비스 이용자를 위한 개인정보 보호 가이드」(2026-05) | AI를 **쓰는 일반 이용자** | 위 안내서와 대상이 다름 |

## 2. AI가 만든 코드·콘텐츠의 권리 문제

| 쟁점 | 알아 둘 점 |
|---|---|
| **AI 생성 코드에 남의 코드가 섞였다면?** | AI가 학습한 오픈소스 코드와 **거의 똑같은 코드**를 낼 수 있습니다. 긴 코드 블록이 어딘가에서 본 듯하면 출처·라이선스를 확인하세요. 일부 도구는 공개 코드와 일치하는 제안을 걸러내는 설정이 있습니다 |
| **오픈 웨이트 모델의 라이선스** | "오픈"이어도 **상업 이용 조건, 사용자 수 제한, 금지 용도**가 붙은 경우가 많습니다. 온프레미스 도입 전에 라이선스 검토 필수 → [법규 유의사항 PDF](../99_참고자료/05_법규_컴플라이언스/서비스_개발운영_법규_유의사항_인턴초급개발자.pdf)의 AI 모델 라이선스 장 참고 |
| **AI 생성물의 저작권** | 사람의 창작적 기여 없이 AI만 만든 결과물은 저작권 보호가 어렵다는 것이 여러 나라의 대체적 입장이지만, 아직 정리 중인 영역입니다. 산출물 납품 계약에 AI 사용 조건이 있는지 확인하세요 |
| **이미지·글을 서비스에 그대로 쓰기** | 실존 인물·브랜드·타인 저작물과 비슷한 결과물은 문제가 될 수 있습니다 |

## 3. AI 기본법 — 웹 개발자가 알아야 할 만큼만

**「인공지능 발전과 신뢰 기반 조성 등에 관한 기본법」** 이 **2026년 1월 22일** 시행되었습니다.

| 내용 | 웹 개발자에게 의미 |
|---|---|
| 생성형 AI·고영향 AI 기반 제품·서비스를 제공할 때 **이용자에게 사전 고지** | 화면에 "이 기능은 생성형 AI를 사용합니다" 같은 **안내 UI** |
| AI 생성물 **표시** 의무 (특히 실제와 구분하기 어려운 딥페이크류는 명확한 표시) | 결과물에 "AI 생성" 라벨, 이미지라면 워터마크 등 |
| **고영향 AI**(사람의 생명·안전·기본권에 큰 영향을 주는 영역)에 안전성·신뢰성 확보 조치 | 채용·대출 심사·공공서비스 대상자 선정 같은 기능이라면 **사람이 최종 결정**하는 흐름 설계가 중요 |
| 과태료·사실조사는 **최소 1년 계도기간** 운영 (정부 발표) | 2026년 11월 현재 계도기간이 곧 끝날 수 있으므로 **최신 집행 방침 확인 필요** |

- 의무의 주된 대상은 AI를 **개발·제공하는 사업자**입니다. 우리가 만든 서비스가 해당하는지, 어떤 조치가 필요한지는 **법무 검토** 사항입니다. 개발자는 "이런 요구사항이 들어올 수 있다"는 것을 알고 있으면 됩니다.
- EU에 서비스하는 경우 EU AI Act도 적용될 수 있습니다.

> 출처: [대한민국 정책브리핑 — AI 기본법 시행](https://korea.kr/news/policyNewsView.do?newsId=148958380) (정부 발표, 1차). 세부 해설은 언론·로펌 자료(2차)를 참고했습니다.

## 4. 매일 쓰는 안전 체크 (붙여 두고 쓰세요)

```
AI에 붙여 넣기 전 5초 체크
 □ 이 도구는 회사가 승인한 도구·계정인가?
 □ 비밀번호·키·토큰이 없는가?
 □ 실제 개인정보(이름·전화·주민번호·주소·이메일)가 없는가?
 □ 내부 IP·서버명·고객 기관 정보가 없는가?
 □ 꼭 필요한 부분만 넣었는가?

AI 결과를 쓰기 전 체크
 □ 내가 한 줄씩 설명할 수 있는가?
 □ 실행·테스트로 확인했는가?
 □ 버전에 맞는 공식 문서와 대조했는가?
 □ 추천받은 라이브러리가 실제로 존재하고 정상 관리되는가?
 □ 긴 코드가 어딘가의 코드를 그대로 베낀 것 같지 않은가?
```

## 5. 면접 대비 — AI 관련 질문

정답이 있는 질문보다 **"자기 생각 + 근거"** 를 보는 질문이 많습니다. 아래 예시 답은 방향을 잡는 용도로만 쓰고 **자기 경험으로 바꿔서** 말하세요.

<details>
<summary>Q1. AI 코딩 도구를 어떻게 사용하나요?</summary>

- 포인트: **"쓴다/안 쓴다"보다 "어떻게 검증하는지"** 를 말하기.
- 예: "에러 해석과 낯선 코드 설명에 주로 씁니다. 받은 코드는 실행과 테스트로 확인하고, 설명할 수 없는 코드는 커밋하지 않는 것을 원칙으로 합니다. 실제로 AI가 Spring Security 6에서 제거된 클래스를 쓴 코드를 준 적이 있어서, 질문할 때 버전을 꼭 명시합니다."
</details>

<details>
<summary>Q2. LLM의 할루시네이션은 왜 생기나요? 어떻게 줄이나요?</summary>

- LLM은 사실을 찾는 것이 아니라 **그럴듯한 다음 토큰을 확률적으로 생성**하기 때문입니다.
- 줄이는 방법: 근거 자료를 넣어 주는 **RAG**, 출처를 함께 표시, 출력 형식 제한과 검증, 중요한 결정은 사람이 확인.
</details>

<details>
<summary>Q3. RAG와 파인튜닝의 차이는?</summary>

- RAG: 질문할 때마다 **관련 문서를 검색해 프롬프트에 넣음**. 최신 정보 반영이 쉽고 출처 제시 가능. 모델은 그대로.
- 파인튜닝: 모델 자체를 **추가 학습**. 말투·형식 특화에 유리. 정보가 바뀌면 재학습 필요.
- 사내 문서 Q&A처럼 **자주 바뀌는 정보는 보통 RAG**가 적합.
</details>

<details>
<summary>Q4. 웹 서비스에 LLM 기능을 붙일 때 주의할 점은?</summary>

- 중요한 순서로: ① **API 키는 서버에만**(프론트 노출 금지) ② **타임아웃·재시도·실패 시 대체 응답** ③ **출력 검증**(XSS, 형식) ④ **프롬프트 인젝션 대비 — 권한 최소화** ⑤ **사용량 제한과 비용 모니터링** ⑥ 개인정보를 프롬프트에 넣지 않기, AI 생성 표시.
</details>

<details>
<summary>Q5. 프롬프트 인젝션이 뭔가요?</summary>

- 사용자 입력이나 외부 문서에 **AI에게 주는 지시를 숨겨** 원래 지시를 무시하게 만드는 공격. SQL 인젝션과 비슷하게 "데이터와 명령이 섞여서" 생김.
- 완벽한 차단법이 없으므로 **AI가 속아도 피해가 작게** — 권한 최소화, 위험 행동 사람 승인, 민감정보 미포함.
</details>

<details>
<summary>Q6. LLM API는 상태를 기억하나요?</summary>

- 기본적으로 **stateless**. 챗봇은 매 요청마다 이전 대화를 함께 보내서 기억하는 것처럼 보임. 그래서 대화가 길수록 입력 토큰과 비용이 늘어남. HTTP가 stateless라서 세션·토큰으로 상태를 유지하는 것과 같은 구조.
</details>

<details>
<summary>Q7. AI가 개발자를 대체할까요?</summary>

- 정답이 없는 질문. **근거를 들어 균형 있게** 말하기.
- 예: "반복적인 코드 작성은 AI가 많이 가져갈 것 같습니다. 하지만 개발자 설문에서 AI 사용률은 80%가 넘는데 정확도를 신뢰하는 사람은 3분의 1 정도였습니다. 결국 무엇을 만들지 정하고, 결과를 검증하고, 책임지는 일은 사람에게 남는다고 생각합니다. 그래서 저는 요구사항을 명확히 정리하는 능력과 코드를 검증하는 능력을 키우려고 합니다."
</details>

<details>
<summary>Q8. 공공기관 프로젝트에서 AI를 쓰려면 무엇을 고려해야 하나요?</summary>

- 망분리·보안 규정 때문에 **외부 AI API 사용이 제한**될 수 있음 → 사내 설치형(온프레미스) 모델 검토, 이때 **모델 라이선스** 확인.
- 개인정보가 많은 업무 → 프롬프트에 개인정보를 넣지 않는 설계, 가명처리.
- AI 기본법의 **고지·표시**, 국민에게 영향이 큰 결정은 **사람이 최종 판단**하는 흐름.
</details>
