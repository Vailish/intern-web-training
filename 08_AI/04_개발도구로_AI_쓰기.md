# 04. 개발 도구로 AI 쓰기 ⭐ 실무

> 🎯 목표: AI 코딩 도구를 **실력을 키우는 방향으로** 쓰는 습관을 들인다. 좋은 질문(프롬프트)을 쓰고, 받은 결과를 **검증**하고, **넣으면 안 되는 정보**를 구분한다.

---

## 도입 — 같은 도구, 다른 결과

| 인턴 A | 인턴 B |
|---|---|
| 에러가 나면 통째로 붙여 넣고 "고쳐줘" | 에러 전문 + 버전 + 내가 시도한 것 + "원인 후보를 알려줘" |
| 받은 코드를 그대로 붙여 넣고 커밋 | 실행하고, 테스트하고, **한 줄씩 설명할 수 있을 때** 커밋 |
| 3개월 뒤: AI 없이는 에러를 못 읽음 | 3개월 뒤: AI 덕분에 **더 빨리 배움** |

AI는 **실력을 키우는 도구도, 실력을 갉아먹는 도구도** 될 수 있습니다. 차이는 쓰는 방식입니다.

---

## 1. AI 코딩 도구의 세 가지 형태

| 형태 | 하는 일 | 예 (2026년 11월 기준, 제품은 자주 바뀜) | 인턴에게 |
|---|---|---|---|
| **채팅형** | 질문하면 설명·코드를 글로 줌. 실행은 사람이 | 웹 챗봇(ChatGPT, Claude, Gemini 등) | **학습용으로 가장 좋음.** 개념 질문, 에러 해석 |
| **IDE 보조형** | 코드를 치는 중에 다음 줄 자동완성, 선택 영역 설명·수정 | GitHub Copilot, IDE 내장 AI | 편하지만 **생각 없이 Tab 누르기 쉬움** |
| **에이전트형** | 목표를 주면 파일을 읽고, 고치고, 명령·테스트를 실행 | Claude Code, OpenAI Codex, Cursor 에이전트 등 | 강력하지만 **무엇을 바꿨는지 반드시 검토** |

> ⚠️ **어떤 도구를 써도 되는지는 회사가 정합니다.** 사내 코드를 다룰 때는 **회사가 승인한 도구·계정**만 쓰세요. 개인 무료 계정은 입력이 학습에 쓰이거나 보관될 수 있습니다 (06).

## 2. 인턴을 위한 사용 원칙 (중요한 순서)

### 원칙 1. 설명할 수 없는 코드는 커밋하지 않는다

코드 리뷰에서 "이 줄은 왜 필요해요?"라고 물으면 답할 수 있어야 합니다. "AI가 그렇게 줬어요"는 답이 아닙니다.
**모르는 부분은 AI에게 "이 줄이 왜 필요한지 설명해 줘"라고 되물으세요.** 이게 AI를 가장 잘 쓰는 방법입니다.

### 원칙 2. 검증은 내 몫이다

AI의 답은 **"검증 전의 가설"** 입니다. 검증 수단을 정해 두세요.

| AI가 준 것 | 검증 방법 |
|---|---|
| 코드 | **실행해 본다.** 테스트를 돌린다 ([Testing 모듈](../Spring/Testing/README.md)) |
| 설정·API 사용법 | **공식 문서**에서 해당 버전 페이지를 확인한다 |
| 에러 원인 분석 | 원인 후보를 **하나씩 확인**한다 (예: [07_Network 06](../07_Network/06_에러로_원인찾기.md)의 순서대로) |
| 라이브러리 추천 | Maven Central·npm에 **실제로 있는지**, 관리되고 있는지 확인 |
| 개념 설명 | 교재·공식 문서와 대조한다. 숫자·날짜·법 조항은 **특히 의심** |

### 원칙 3. 버전을 항상 밝힌다

AI는 학습 데이터에 많이 나온 **옛날 버전 코드**를 자주 줍니다. 이 교육과정에서 실제로 겪은 함정들이 대표적입니다.

| 이 교육과정의 실제 함정 | AI가 흔히 주는 옛날 답 |
|---|---|
| Spring Security 7 설정 ([Security 모듈](../Spring/Security/README.md)) | `WebSecurityConfigurerAdapter` 상속 (Security 6에서 제거됨) |
| Spring Boot 4의 Jackson 3 ([실시간채팅](../ETC/실시간채팅/)) | Jackson 2 패키지(`com.fasterxml.jackson.databind`) 기준 코드 |
| Boot 4에서 패키지가 옮겨진 테스트 어노테이션 ([Testing 모듈](../Spring/Testing/README.md)) | Boot 3 기준 import 경로 |

> 💡 질문 첫 줄에 항상 **"Java 17, Spring Boot 4.1, Gradle 기준"** 처럼 환경을 적으세요.

### 원칙 4. 학습 중인 주제는 "정답" 대신 "힌트"를 달라고 한다

- 알고리즘 연습([05_algorithm](../05_algorithm/))처럼 **내 머리로 풀어야 실력이 느는 것**은 AI를 끄고 푸세요. 코딩 테스트는 대부분 AI 사용이 금지입니다.
- 막혔을 때는 "정답 코드 말고, **어떤 방향으로 생각해야 하는지 힌트만** 줘"라고 요청하세요.

### 원칙 5. 넣으면 안 되는 것을 안다

**사내 소스코드, 고객·개인정보, 비밀번호·API 키, 내부 IP·서버 주소, 계약·영업 정보**는 승인되지 않은 AI 도구에 넣지 않습니다.
에러 로그를 붙여 넣을 때도 **IP, 계정, 개인정보를 지우고** 넣으세요. 자세한 기준은 [06 문서](./06_안전하게_쓰기_보안_법규.md).

## 3. 좋은 프롬프트의 구조

```
[상황]   Java 17, Spring Boot 4.1, Gradle. 게시판 CRUD를 JPA로 만드는 중이다.
[문제]   서버를 실행하면 아래 에러가 난다. (에러 전문 — 개인정보·IP는 지움)
[시도]   application.yml의 datasource url을 확인했고, H2 콘솔은 접속된다.
[요청]   원인 후보를 가능성 높은 순서로 3개 알려주고, 각각 확인하는 방법을 알려줘.
[형식]   코드는 수정이 필요한 부분만. 왜 그런지 한 줄씩 설명해줘.
```

| 요소 | 빠지면 생기는 일 |
|---|---|
| **상황(버전·환경)** | 옛날 버전 답을 받음 |
| **문제(에러 전문)** | 에러 한 줄만 주면 엉뚱한 추측을 함. 스택트레이스의 `Caused by:` 가 핵심 |
| **시도한 것** | 이미 해 본 것을 다시 권함 |
| **요청(무엇을 원하는지)** | 원하지 않는 전체 코드 재작성을 받음 |
| **형식** | 장황한 답, 설명 없는 코드 |

## 4. 상황별 프롬프트 템플릿

<details>
<summary>① 에러 해석</summary>

```
Java 17, Spring Boot 4.1 환경이다. 아래 스택트레이스에서
1) 실제 원인이 되는 줄이 어디인지
2) 어느 계층(설정/DB/네트워크/코드) 문제인지
3) 내가 먼저 확인할 것 3가지
를 알려줘. 코드를 고쳐주지는 말고 원인 파악을 도와줘.

(스택트레이스 — 개인정보·IP·비밀번호 지움)
```
</details>

<details>
<summary>② 코드 설명 (남의 코드·AI가 준 코드 이해하기)</summary>

```
아래 코드를 신입 개발자에게 설명하듯 한 줄씩 설명해줘.
특히 어노테이션이 하는 일과, 이 코드가 없으면 어떤 문제가 생기는지 알려줘.
```
</details>

<details>
<summary>③ 코드 리뷰 받기</summary>

```
아래 컨트롤러 코드를 리뷰해줘. 관점은
1) 버그 가능성  2) 보안(입력 검증, SQL 인젝션, 권한)  3) 예외 처리
중요한 순서로 3개만 지적하고, 각각 왜 문제인지 설명해줘.
```
</details>

<details>
<summary>④ 테스트 작성</summary>

```
Spring Boot 4.1, JUnit 5 기준. 아래 Service 메서드의 단위 테스트를 작성해줘.
정상 케이스 1개, 경계값 1개, 예외 케이스 1개.
각 테스트가 무엇을 검증하는지 주석으로 적어줘.
```
> 받은 테스트가 **실제로 실패할 수 있는지**도 확인하세요. 코드를 일부러 틀리게 바꿔서 테스트가 빨간불이 되는지 보면, "아무것도 검증하지 않는 테스트"를 걸러낼 수 있습니다.
</details>

<details>
<summary>⑤ 개념 학습 (힌트 모드)</summary>

```
JPA의 영속성 컨텍스트를 공부 중이다. 바로 설명하지 말고,
내가 스스로 이해했는지 확인할 수 있는 질문 3개를 먼저 내줘.
내가 답하면 틀린 부분을 짚어줘.
```
</details>

<details>
<summary>⑥ 커밋 메시지·문서 초안</summary>

```
아래 git diff를 보고 커밋 메시지를 제안해줘.
형식: 첫 줄 50자 이내 요약, 빈 줄, 변경 이유를 2~3줄.
```
> 사내 저장소의 diff라면 **승인된 도구**에서만 하세요.
</details>

## 5. 에이전트형 도구를 쓸 때 추가로 지킬 것

에이전트는 파일을 고치고 명령을 실행합니다. 편한 만큼 위험도 큽니다.

| 수칙 | 이유 |
|---|---|
| **작업 전 git 커밋 또는 브랜치 생성** | 마음에 안 들면 바로 되돌릴 수 있게 |
| **작업을 작게 쪼개서 시킨다** | "게시판 전체 만들어줘"보다 "Entity와 Repository만" 이 검토하기 쉬움 |
| **`git diff`로 변경 내용을 모두 읽는다** | 요청하지 않은 파일까지 고치는 경우가 있음 |
| **삭제·배포·DB 변경 명령은 직접 승인** | 되돌릴 수 없는 작업은 사람이 확인 |
| **프로젝트 규칙 파일을 둔다** | `AGENTS.md`(도구에 따라 `CLAUDE.md` 등)에 빌드 방법·코딩 규칙을 적어 두면 매번 설명할 필요가 줄어듦 |
| **테스트가 통과한다고 끝이 아니다** | AI가 테스트를 통과시키려고 **테스트 쪽을 고치는** 경우도 있음. 테스트 변경도 리뷰 |

## 6. AI에게 시키기 좋은 일 / 조심할 일

| 시키기 좋은 일 | 조심할 일 (사람이 주도) |
|---|---|
| 에러 메시지 해석, 원인 후보 정리 | 보안 설정(인증·권한), 암호화 |
| 낯선 코드 설명 | DB 스키마 변경, 데이터 삭제·마이그레이션 |
| 반복 코드(DTO, 테스트 뼈대) 초안 | 결제·개인정보 처리 로직 |
| 정규식, SQL 초안 작성 (검증 전제) | 법·규정 해석 (법무 확인 필요) |
| 문서·주석·커밋 메시지 초안 | 성능이 중요한 핵심 로직의 최종 결정 |
