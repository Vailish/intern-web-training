# 02. AI 기술 흐름과 트렌드

> 🎯 목표: AI가 **어떤 계기로 지금 여기까지 왔는지** 큰 흐름을 말하고, 2026년 현재 업계의 주요 트렌드가 **웹 개발자에게 어떤 의미인지** 설명할 수 있다.

> ⚠️ **작성 기준: 2026년 11월.** 트렌드는 빠르게 바뀝니다. 날짜·사건은 출처를 확인했지만, "앞으로 어떻게 될까"에 대한 부분은 **작성자의 해석**이니 그대로 믿지 말고 토론 재료로 쓰세요.

---

## 도입

"ChatGPT가 갑자기 나왔다"고 생각하기 쉽지만, 실제로는 **수십 년간 쌓인 기술이 한 지점에서 터진 것**입니다.
흐름을 알면 새 뉴스가 나와도 "아, 이건 그 흐름의 다음 단계구나"하고 자리를 잡아 줄 수 있습니다.

| 2024.11 | Anthropic이 **MCP(Model Context Protocol)** 공개 | AI와 외부 도구를 연결하는 **표준**의 시작 |
| 2025.01 | 중국 DeepSeek가 추론 모델 R1을 오픈 웨이트로 공개 | "적은 비용으로도 최상위권 성능" 충격. 오픈 모델 경쟁 가속 |
| 2025 상반기 | 터미널·IDE에서 파일을 읽고 명령을 실행하는 **코딩 에이전트** 확산 (Claude Code, OpenAI Codex, Cursor 등). "바이브 코딩" 이라는 말 유행 | AI가 **자동완성 → 작업 대행**으로 역할 확대 |
| 2025.05 | Spring AI 1.0 정식(GA) 출시 | **자바·스프링 개발자도** 표준 방식으로 AI 기능을 붙일 수 있게 됨 |

## 2. 2026년 현재의 트렌드 7가지 — 그리고 웹 개발자에게 의미

중요도(웹 개발자 입장) 순으로 정리했습니다.

### ① 챗봇 → 에이전트

- **예전**: 질문하면 답을 글로 준다. 실행은 사람이 한다.
- **지금**: 목표를 주면 AI가 **스스로 도구를 골라 쓰고**(검색, 파일 읽기, 코드 실행, API 호출) 여러 단계를 거쳐 일을 끝낸다.
- **웹 개발자에게**: 코딩 에이전트가 코드를 직접 고치고 테스트까지 돌립니다. 개발자의 역할이 **"직접 타이핑"에서 "명세하고, 검토하고, 검증하는 일"** 로 옮겨 가고 있습니다 (04).

### ② AI 코딩 도구의 일상화 — 하지만 신뢰는 낮다

| 지표 (Stack Overflow 2025 개발자 설문) | 값 |
|---|---|
| AI 도구를 사용 중이거나 사용 예정 | **84%** (2024년 76%) |
| AI 출력의 정확성을 **불신** | **46%** |
| AI 출력의 정확성을 **신뢰** | 33% (매우 신뢰는 3%) |
| 가장 큰 불만: "거의 맞지만 미묘하게 틀린 답" | 45% |

- 또 다른 연구(METR, 2025-07)에서는 **자기 프로젝트를 잘 아는 숙련 개발자 16명**이 AI를 쓸 때 오히려 **19% 느려졌는데**, 본인들은 20% 빨라졌다고 **느꼈습니다.**
  - ⚠️ 표본이 작고 2025년 초 도구 기준이며, 연구진도 "모든 개발자가 느려진다는 뜻은 아니다"라고 밝혔습니다. **"체감과 실제가 다를 수 있다"** 는 교훈으로만 받아들이세요.
- **웹 개발자에게**: 모두가 AI를 쓰지만 **결과를 검증하는 능력**이 차이를 만듭니다. 이것이 04 문서의 핵심입니다.

### ③ 오픈 웨이트 모델과 온프레미스

- 가중치가 공개된 모델을 **우리 서버에서 직접** 돌릴 수 있습니다. 성능 격차도 많이 줄었습니다.
- **웹 개발자에게 (특히 공공·SI)**: 망분리 환경이나 개인정보 때문에 외부 API를 못 쓰는 기관이 많습니다. 이런 곳에서는 **사내 서버의 로컬 LLM**을 쓰는 프로젝트가 늘고 있습니다. 이때도 호출 방식은 대개 **HTTP API**라서 05 문서의 구조가 그대로 통합니다.
- 주의: 오픈 웨이트라고 아무렇게나 써도 되는 것은 아닙니다. 모델마다 **라이선스 조건**이 다릅니다 (06).

### ④ 표준화 — MCP, AGENTS.md

- **MCP**: AI가 DB, 파일, 사내 시스템 같은 외부 도구에 접속하는 방식을 표준화한 규격입니다. "AI용 USB-C"라고 비유하곤 합니다.
- **AGENTS.md**: 코딩 에이전트에게 "이 프로젝트는 이렇게 빌드하고 이 규칙을 따르라"고 알려주는 문서 관례입니다. (도구에 따라 `CLAUDE.md` 등 이름이 다름)
- **웹 개발자에게**: 앞으로는 우리가 만든 백엔드 API를 **사람용 화면**뿐 아니라 **AI 에이전트용 MCP 서버**로도 제공해 달라는 요구가 생길 수 있습니다. 결국 "잘 설계된 API"가 기본이라는 점은 같습니다.

### ⑤ 멀티모달과 추론 모델

- 이미지(스크린샷, 문서 사진), 음성을 입력으로 받는 것이 보통이 되었습니다. 예: 화면 캡처를 주고 "이 레이아웃 HTML로 만들어 줘".
- 추론 모델은 어려운 문제에 강하지만 **느리고 비쌉니다.** 서비스에 붙일 때는 "단순 분류에는 빠르고 싼 모델, 복잡한 분석에는 추론 모델"처럼 **골라 쓰는 설계**가 필요합니다 (05).

### ⑥ 비용과 속도가 설계 요소가 됨

- LLM은 **토큰 단위 과금**이고, 응답에 수 초~수십 초가 걸리기도 합니다.
- **웹 개발자에게**: 기존 API보다 **훨씬 느리고, 호출마다 돈이 드는 외부 API**라고 생각하고 설계해야 합니다. 타임아웃, 스트리밍, 캐싱, 사용량 제한이 필수입니다 (05).

### ⑦ 규제와 신뢰

- 한국은 2026-01-22 **AI 기본법**을 시행했습니다. 생성형 AI 기반 서비스라는 사실의 **사전 고지**, AI 생성물 **표시** 같은 의무가 생겼습니다 (과태료는 최소 1년 계도기간).
- EU는 AI Act를 2024년에 발효해 단계적으로 적용 중이며, 고위험 AI 의무의 적용 시점은 조정 논의가 있었습니다. **최신 일정은 별도 확인이 필요합니다.**
- **웹 개발자에게**: "이 답변은 AI가 생성했습니다" 같은 **표시 UI**, 사람이 최종 확인하는 **흐름 설계**가 기능 요구사항으로 들어오기 시작했습니다 (06).

## 3. 비판적으로 보기 — 트렌드 뉴스를 읽을 때 던질 질문

| 질문 | 이유 |
|---|---|
| **누가** 발표한 수치인가? | 모델 회사의 자체 벤치마크는 유리한 조건일 수 있음 |
| **언제** 기준인가? | 6개월 전 비교표는 이미 낡았을 가능성이 큼 |
| **내 업무 조건**과 같은가? | 영어·파이썬 위주 벤치마크가 한국어·eGovFrame 업무에도 맞는지는 별개 |
| 체감인가, 측정인가? | METR 연구처럼 **체감과 측정이 반대**인 경우가 있음 |
| "AI가 개발자를 대체한다"는 주장의 근거는? | 실제로 바뀌는 것은 **일의 구성**(타이핑 ↓, 명세·검증·리뷰 ↑)이라는 시각이 더 많음. 단, 이 역시 아직 결론 난 문제가 아님 |
