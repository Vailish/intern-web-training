## 1. 레이스 컨디션 — `count++` 한 줄도 안전하지 않다

**레이스 컨디션(경쟁 상태)**: 여러 스레드가 **공유 데이터**를 동시에 읽고 쓸 때, **실행 순서(타이밍)에 따라 결과가 달라지는** 현상.

`count++` 는 한 줄이지만 CPU 입장에서는 3단계입니다.

```
           스레드 A                     스레드 B              count (메모리)
  ① 읽기   count 를 읽음 → 5                                      5
  ① 읽기                                count 를 읽음 → 5          5
  ② 계산   5 + 1 = 6                    5 + 1 = 6
  ③ 쓰기   count 에 6 저장                                        6
  ③ 쓰기                                count 에 6 저장            6   ← 2번 더했는데 1만 늘었다!
```

### 🧪 직접 실행해 보기

스레드 4개가 각각 10만 번씩 `count++` 를 합니다. 기대값은 40만입니다.

```powershell
java "-Dfile.encoding=UTF-8" RaceConditionLab.java
```
```
스레드 4개 × 각 100,000번 증가 → 기대값 400,000

[volatile만     ] 1회차 결과     221,467  (잃어버린 증가 178,533)  11ms
[volatile만     ] 2회차 결과     185,578  (잃어버린 증가 214,422)  10ms
[volatile만     ] 3회차 결과     190,289  (잃어버린 증가 209,711)  5ms
[volatile만     ] 4회차 결과     186,632  (잃어버린 증가 213,368)  4ms
[volatile만     ] 5회차 결과     118,733  (잃어버린 증가 281,267)  5ms
[synchronized   ]       결과     400,000  22ms
[AtomicInteger  ]       결과     400,000  7ms
```

관찰할 것:
1. 잠금이 없으면 **실행할 때마다 값이 다르고**, 절반 넘게 사라지기도 합니다. **에러도 경고도 없습니다.**
2. `volatile` 을 붙여도 소용없습니다(아래 3절).
3. `synchronized` 와 `AtomicInteger` 는 **항상 정확**합니다. 대신 조금 느립니다.

스레드를 1개로 주면 어떻게 될까요?
```powershell
java "-Dfile.encoding=UTF-8" RaceConditionLab.java 1 100000
```
```
[volatile만     ] 1회차 결과     100,000  (잃어버린 증가 0)  0ms
```

**혼자 테스트하면 절대 안 보입니다.** "제 PC에서 해 봤는데 괜찮던데요"가 동시성 버그에서는 증거가 되지 못하는 이유입니다.

> 🔍 **실측하며 겪은 함정**: 처음엔 `volatile` 없는 평범한 `int` 필드로 만들었는데, 회차가 지날수록 손실이 0으로 나왔습니다. JIT 컴파일러(01 문서)가 반복문을 최적화해 **값을 레지스터에 모아 한 번에 더해 버려서** 스레드가 겹칠 틈이 사라진 것입니다. 버그가 없어진 게 아니라 **타이밍상 숨은 것**입니다. 동시성 버그가 "가끔만" 나타나는 이유가 바로 이런 것입니다.

## 2. 해결 ① — 임계 구역을 한 번에 한 스레드만

**임계 구역(critical section)**: 공유 데이터를 읽고 쓰는 코드 구간. 여기를 **한 번에 한 스레드만** 실행하게 막으면(상호 배제) 레이스 컨디션이 사라집니다.

### `synchronized` — 자바의 기본 잠금

```java
static class SyncCounter {
    private int count = 0;
    synchronized void increment() { count++; }   // 이 객체의 잠금을 얻은 스레드만 들어옴
    synchronized int get() { return count; }
}
```

- 한 스레드가 들어가 있으면 다른 스레드는 **문 앞에서 기다립니다**(`BLOCKED` 상태).
- 간단하고 확실하지만, 기다리는 스레드가 많아지면 느려집니다. **잠그는 범위는 최대한 좁게.**

### `AtomicInteger` — 잠금 없이 원자적으로

```java
private final AtomicInteger count = new AtomicInteger();
void increment() { count.incrementAndGet(); }
```

- CPU의 **CAS(Compare-And-Swap)** 명령을 씁니다: "값이 아직 5이면 6으로 바꿔라, 누가 먼저 바꿨으면 다시 시도".
- 숫자 하나를 세는 정도라면 `synchronized` 보다 가볍습니다(실측 22ms vs 7ms).

### 자바가 제공하는 스레드 안전한 도구

| 하고 싶은 것 | ❌ 위험 | ✅ 안전 |
|---|---|---|
| 숫자 세기 | `int count; count++` | `AtomicInteger`, `AtomicLong`, `LongAdder` |
| 여러 스레드가 쓰는 Map | `HashMap` | `ConcurrentHashMap` |
| 여러 스레드가 쓰는 List | `ArrayList` | `CopyOnWriteArrayList` (읽기 위주일 때), `Collections.synchronizedList` |
| 날짜 형식 변환 | `SimpleDateFormat` 을 필드로 공유 | `DateTimeFormatter` (불변이라 공유해도 안전) |

> 💡 `SimpleDateFormat` 은 내부에 상태를 가지고 있어서 여러 스레드가 공유하면 날짜가 엉망이 됩니다. 옛날 코드(특히 전자정부프레임워크 기반 레거시)에서 `static SimpleDateFormat` 을 보면 의심하세요. 새 코드는 `java.time` 의 `DateTimeFormatter` 를 씁니다.

## 3. `volatile` 은 잠금이 아니다

면접 단골이자 실무 착각 1순위입니다.

| | 보장하는 것 | 보장하지 않는 것 |
|---|---|---|
| `volatile` | **가시성**: 한 스레드가 쓴 값을 다른 스레드가 **바로 볼 수 있음** (CPU 캐시에만 두지 않고 메모리에 반영) | **원자성**: 읽기→계산→쓰기를 한 덩어리로 묶어 주지 않음 |
| `synchronized` | 가시성 + 원자성 | |

- `volatile` 이 맞는 곳: **한 스레드만 쓰고 나머지는 읽기만** 하는 플래그. 예: `volatile boolean running = true;` 로 작업 스레드를 멈추게 하기.
- `count++` 처럼 **읽고 고쳐서 쓰는** 곳에는 `volatile` 로 부족합니다. 위 실측이 증거입니다.

## 4. 스프링 실무 — 싱글톤 빈은 "무상태(stateless)"로

03 문서의 그림을 떠올리세요. **필드는 힙에 있어서 모든 요청 스레드가 공유**하고, **지역 변수는 스레드마다 따로** 있습니다.

```java
// ❌ 요청마다 바뀌는 값을 필드에 저장
@Service
public class OrderService {
    private Member currentMember;          // 모든 요청이 공유!
    private int totalPrice;                // 모든 요청이 공유!
}

// ✅ 필드에는 "변하지 않는 협력 객체"만, 요청 데이터는 파라미터와 지역 변수로
@Service
@RequiredArgsConstructor
public class OrderService {
    private final OrderRepository orderRepository;   // final, 주입 후 안 바뀜 → 안전

    public OrderResult order(Long memberId, OrderRequest req) {
        Member member = ...;                           // 지역 변수 → 안전
        int totalPrice = ...;                          // 지역 변수 → 안전
    }
}
```

### 싱글톤 빈 점검 규칙

| 필드에 있어도 되는 것 | 필드에 있으면 안 되는 것 |
|---|---|
| `final` 로 주입받은 Repository, 다른 Service | 로그인 사용자, 요청 파라미터, 계산 중간값 |
| 설정값 (`@Value` 로 받은 URL 등, 안 바뀜) | 요청마다 바뀌는 카운터, 리스트 |
| 불변 객체 (`DateTimeFormatter`, `ObjectMapper` 등 스레드 안전하다고 문서화된 것) | `SimpleDateFormat`, `HashMap` 같은 스레드 안전하지 않은 객체 |

> 💡 **리뷰 습관**: `@Service`, `@Controller`, `@Component` 클래스를 열면 **`final` 이 아닌 필드부터** 찾아보세요. 그게 있으면 "이 값은 여러 요청이 동시에 바꿔도 괜찮은가?"를 물어야 합니다.

### 서버가 2대면? — `synchronized` 의 한계

`synchronized` 와 `AtomicInteger` 는 **한 JVM(프로세스) 안**에서만 통합니다. 서버를 2대로 늘리면(스케일 아웃) 각 서버의 잠금은 서로를 모릅니다.

```
서버 1: synchronized 로 잠금 → 재고 1개 확인 → 주문 성공
서버 2: synchronized 로 잠금 → 재고 1개 확인 → 주문 성공     ← 재고 1개를 2명이 삼
```

- 여러 서버가 공유하는 데이터(재고, 잔액, 좌석)는 **DB에서 지켜야** 합니다 → 06 문서의 `UPDATE ... SET x = x - 1`, `SELECT ... FOR UPDATE`.
- 그래서 실무 웹 서버는 **애초에 상태를 앱 메모리에 두지 않고**(무상태) DB·Redis 같은 공유 저장소에 둡니다. 로그인 세션을 서버 메모리에 두면 서버 증설이 어려운 것도 같은 이유입니다([Security](../Spring/Security/README.md)의 세션 vs JWT 비교).

## 5. 데드락 — 서로를 기다리며 영원히 멈춤

**데드락(교착 상태)**: 두 스레드가 **서로 상대가 가진 잠금을 기다리며** 아무도 진행하지 못하는 상태.

```
이체1 (A→B): A 계좌 잠금 ✅ ──▶ B 계좌 잠금 기다림 ⏳ ─┐
                                                       │  서로가 서로를 기다림
이체2 (B→A): B 계좌 잠금 ✅ ──▶ A 계좌 잠금 기다림 ⏳ ─┘  → 영원히 멈춤
```

### 🧪 직접 실행해 보기

```powershell
java "-Dfile.encoding=UTF-8" DeadlockLab.java
```
```
=== 데드락 버전: 서로 반대 순서로 잠금 ===
이체2(B→A): 첫 번째 계좌 잠금 획득, 두 번째 계좌를 기다리는 중...
이체1(A→B): 첫 번째 계좌 잠금 획득, 두 번째 계좌를 기다리는 중...

🔒 데드락 감지! (jstack 으로 보면 'Found one Java-level deadlock' 으로 나오는 상황)
  스레드 'transfer-A-to-B' 상태=BLOCKED, 기다리는 잠금=java.lang.Object@6a28ffa4, 그 잠금을 가진 스레드='transfer-B-to-A'
  스레드 'transfer-B-to-A' 상태=BLOCKED, 기다리는 잠금=java.lang.Object@3f197a46, 그 잠금을 가진 스레드='transfer-A-to-B'
```

> 이 실습 코드는 JVM 기능(`ThreadMXBean`)으로 데드락을 찾아 보여 주고 스스로 종료합니다. 실제 데드락은 **에러도 로그도 없이 그냥 멈춥니다.** CPU 사용률도 0%에 가깝습니다.

### 데드락의 4가지 조건 — 하나만 깨면 된다

| 조건 | 뜻 | 깨는 방법 |
|---|---|---|
| 상호 배제 | 잠금은 한 번에 한 스레드만 가짐 | (보통 못 깸 — 잠금의 본질) |
| 점유 대기 | 하나를 쥔 채로 다른 걸 기다림 | 필요한 잠금을 한 번에 다 얻기 |
| 비선점 | 남의 잠금을 뺏을 수 없음 | **타임아웃** 두고 포기 (`tryLock(시간)`, DB 잠금 대기 시간) |
| **순환 대기** | A는 B를, B는 A를 기다리는 원형 | **잠금 순서를 통일** ← 가장 실용적 |

해결 버전 (항상 A → B 순서로 잠금):
```powershell
java "-Dfile.encoding=UTF-8" DeadlockLab.java fixed
```
```
=== 해결 버전: 항상 A → B 순서로 잠금 ===
이체1(A→B): 두 계좌 모두 잠금 획득 → 이체 완료
이체2(B→A): 두 계좌 모두 잠금 획득 → 이체 완료
→ 두 이체 모두 정상 완료. 데드락 없음.
```

실무 규칙 예: **"두 계좌를 잠글 땐 항상 계좌번호가 작은 쪽부터."** 이체 방향과 상관없이 순서가 같아집니다.

### 서버가 멈췄을 때 — 스레드 덤프 뜨기

```powershell
jps -l                    # 멈춘 앱의 PID 찾기
jstack <PID>              # 또는 jcmd <PID> Thread.print
```
- 데드락이 있으면 출력 끝에 **`Found one Java-level deadlock:`** 과 함께 누가 무엇을 기다리는지 나옵니다(실측).
  ```
  Found one Java-level deadlock:
  =============================
  "t1":
    waiting to lock monitor 0x000001e39c426060 (object 0x0000000622a211f0, a java.lang.Object),
    which is held by "t2"
  ```
- `java X.java` 처럼 소스 파일로 바로 실행한 프로그램은 `jps -l` 에서 클래스 이름이 아니라 **`jdk.compiler/com.sun.tools.javac.launcher.Main`** 으로 보입니다. 스프링 앱(`java -jar`)은 jar 이름으로 보입니다.
- **재시작하기 전에 먼저 덤프부터** 뜨세요. 재시작하면 원인 증거가 사라집니다.

> 💡 DB에도 데드락이 있습니다. 두 트랜잭션이 행을 반대 순서로 잠그면 생기며, DB는 보통 이를 감지해 **한쪽을 강제로 실패시킵니다**(MySQL: `Deadlock found when trying to get lock`). 해결 원칙은 같습니다: **같은 순서로 잠그기, 트랜잭션을 짧게.**

## 6. 함정

| 오해·증상 | 실제 |
|---|---|
| "로컬에서 여러 번 해 봤는데 괜찮았다" | 동시성 버그는 **동시 요청**이 있어야 나타남. 혼자 테스트로는 증명 불가 |
| "`volatile` 붙였으니 안전하다" | 가시성만 보장. `count++` 는 여전히 깨짐 |
| "싱글톤 빈에 필드 하나쯤은 괜찮겠지" | 요청마다 바뀌는 값이면 **다른 사용자의 데이터가 섞임** (실측 20건 중 18건) |
| "`synchronized` 붙였으니 재고 문제 해결" | 서버가 2대 이상이면 무용지물. 공유 데이터는 DB에서 지키기 |
| 서버가 멈춰서 일단 재시작 | 재시작 전에 **스레드 덤프**를 떠야 원인을 찾을 수 있음 |
| "잠금을 넓게 걸면 더 안전하다" | 대기 시간이 늘고 데드락 위험도 커짐. **좁게, 짧게, 같은 순서로** |
