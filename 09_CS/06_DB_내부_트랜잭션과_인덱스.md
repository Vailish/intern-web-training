# 06. DB 내부 — 트랜잭션과 인덱스

> 🎯 목표: 트랜잭션을 써도 **갱신 분실(lost update)** 이 생기는 이유와 해결법 두 가지를 직접 재현하고, 인덱스가 **언제 쓰이고 언제 안 쓰이는지** 실행 계획으로 확인한다.

> 📌 선수 학습: [03_Database 04 — JDBC 실습](../03_Database/04_JDBC_실습.md)의 **Step 6 트랜잭션(commit/rollback)**. 이 문서는 그다음 단계입니다.

---

## 도입 — 트랜잭션을 썼는데 3,000원이 사라졌다

잔액 10,000원 계좌에서 두 사람이 거의 동시에 3,000원과 5,000원을 출금합니다. 정답은 2,000원입니다.
두 출금 모두 **트랜잭션 안에서** `SELECT` → 자바에서 계산 → `UPDATE` → `commit` 했습니다.

```
최종 잔액 = 5000원  (정답 2,000원)  ← 3,000원 출금이 사라짐
```

트랜잭션은 "전부 성공 아니면 전부 취소"라고 배웠는데, 왜 이런 일이 생길까요?

---

## 1. 트랜잭션 복습 — ACID

| 성질 | 뜻 | 예 |
|---|---|---|
| **A**tomicity 원자성 | 전부 성공하거나 전부 취소 | 이체 중 출금만 되고 입금이 실패하면 출금도 취소 |
| **C**onsistency 일관성 | 규칙(제약 조건)을 깨는 상태로 끝나지 않음 | 잔액이 음수가 될 수 없음 |
| **I**solation 격리성 | 동시에 실행되는 트랜잭션끼리 서로 얼마나 안 보이게 할지 | ← **오늘의 주제** |
| **D**urability 지속성 | 커밋한 것은 서버가 꺼져도 남음 | |

03_Database에서 배운 commit/rollback은 **A(원자성)** 입니다. 도입의 문제는 **I(격리성)**, 즉 **동시에 여러 트랜잭션이 돌 때**의 문제입니다. 04 문서의 레이스 컨디션이 **DB에서 일어난 것**입니다.

---

## 2. 격리 수준 — 얼마나 "안 보이게" 할 것인가

완벽하게 격리하면(한 번에 한 트랜잭션만) 안전하지만 느립니다. 그래서 DB는 **격리 수준**을 골라 쓰게 합니다.

| 격리 수준 | Dirty Read | Non-Repeatable Read | Phantom Read | 기본값으로 쓰는 DB |
|---|---|---|---|---|
| READ UNCOMMITTED | 발생 | 발생 | 발생 | (거의 안 씀) |
| **READ COMMITTED** | 방지 | 발생 | 발생 | Oracle, PostgreSQL, SQL Server, **H2 (실측)** |
| **REPEATABLE READ** | 방지 | 방지 | 발생 가능* | **MySQL (InnoDB)** |
| SERIALIZABLE | 방지 | 방지 | 방지 | |

\* MySQL InnoDB는 REPEATABLE READ에서도 대부분의 팬텀 읽기를 막도록 구현돼 있습니다. 세부 동작은 [MySQL 공식 문서](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html)를 확인하세요.

| 현상 | 뜻 |
|---|---|
| **Dirty Read** | 다른 트랜잭션이 **커밋하지 않은** 값을 읽음 (나중에 롤백되면 없는 값을 본 셈) |
| **Non-Repeatable Read** | 같은 트랜잭션에서 같은 행을 두 번 읽었는데 값이 다름 (그 사이 누가 수정·커밋) |
| **Phantom Read** | 같은 조건으로 두 번 조회했는데 **행 개수**가 다름 (그 사이 누가 추가·커밋) |

> 💡 **로컬은 H2, 운영은 MySQL** 이면 기본 격리 수준이 다릅니다([Spring/Database](../Spring/Database/README.md)의 H2→MySQL 전환). 동시성 관련 동작은 로컬에서 확인한 것과 운영이 다를 수 있다는 점을 기억하세요.

### 그런데 — 격리 수준이 갱신 분실을 막아 주지는 않는다

도입의 문제는 위 세 현상 중 어느 것도 아닙니다. 둘 다 **커밋된 값을 정상적으로 읽었고**, 각자 **자기가 계산한 값을 정상적으로 썼을 뿐**입니다. 문제는 **"읽은 뒤 쓰기 전까지" 다른 트랜잭션이 끼어든 것**이고, 이를 **갱신 분실(Lost Update)** 이라고 합니다. 격리 수준 기본값(READ COMMITTED, MySQL의 REPEATABLE READ 포함)에서는 이 코드 패턴을 **개발자가 직접** 막아야 합니다.

## 3. 🧪 갱신 분실 재현과 해결 두 가지

```powershell
cd 09_CS\샘플\cs-lab
java -cp "../../../03_Database/샘플/jdbc/lib/h2-2.3.232.jar" "-Dfile.encoding=UTF-8" LostUpdateLab.java
```

> 03_Database 모듈의 H2 드라이버를 그대로 씁니다. **인메모리 DB**(`jdbc:h2:mem:`)라 실행이 끝나면 데이터가 사라지고 파일도 남지 않습니다.

### ❌ 읽고 → 자바에서 계산 → 덮어쓰기

```java
int bal = select("SELECT balance FROM account WHERE id = 1");   // 10000
update("UPDATE account SET balance = ? WHERE id = 1", bal - 3000);
commit();
```
```
격리 수준(이 DB 기본값) = READ COMMITTED

=== 1. ❌ 읽고 → 자바에서 계산 → 덮어쓰기 ===
[A] 잔액 조회: 10000
[B] 잔액 조회: 10000   (A가 아직 커밋 전이라 B도 10,000을 봄)
[A] 10000 - 3000 = 7000 저장, 커밋
[B] 10000 - 5000 = 5000 저장, 커밋   ← A의 결과를 덮어씀
최종 잔액 = 5000원  (정답 2,000원)  ← 3,000원 출금이 사라짐
```

B는 **이미 낡은 값(10,000)** 으로 계산해서 A의 결과를 덮어썼습니다. 04 문서의 `count++` 3단계와 정확히 같은 구조입니다.

### ✅ 해결 1 — 계산을 UPDATE 한 문장 안에서

```sql
UPDATE account SET balance = balance - ? WHERE id = 1 AND balance >= ?
```
```
=== 2. ✅ UPDATE 한 문장으로 계산까지 DB에서 ===
[A] UPDATE ... balance - 3000 → 변경된 행 1
[B] UPDATE ... balance - 5000 → 변경된 행 1
최종 잔액 = 2000원
```

- DB가 **한 문장 안에서** 현재 값을 읽고 빼고 씁니다. 그 사이에 아무도 못 끼어듭니다.
- `AND balance >= ?` 로 잔액 부족을 함께 검사합니다. **변경된 행이 0이면** 잔액 부족 → 자바에서 예외 처리.
- 재고 차감(`stock = stock - 1`), 조회수 증가(`view_count = view_count + 1`) 모두 이 방식이 가장 간단하고 빠릅니다.

### ✅ 해결 2 — `SELECT ... FOR UPDATE` 로 읽을 때 잠그기 (비관적 락)

자바에서 복잡한 검증을 해야 해서 한 문장으로 못 쓸 때 씁니다.

```sql
SELECT balance FROM account WHERE id = 1 FOR UPDATE   -- 이 행을 잠금. 커밋/롤백 때 풀림
```
```
=== 3. ✅ SELECT ... FOR UPDATE 로 행 잠그기 ===
[A]    1ms SELECT ... FOR UPDATE 시도
[A]    5ms 잠금 획득, 잔액 10000
[B]    6ms SELECT ... FOR UPDATE 시도
[A] 1016ms 10000 - 3000 = 7000 저장, 커밋 (잠금 해제)
[B] 1016ms 잠금 획득, 잔액 7000              ← B는 1초 동안 기다렸다가, A가 바꾼 7000을 읽음
[B] 2022ms 7000 - 5000 = 2000 저장, 커밋 (잠금 해제)
최종 잔액 = 2000원
```

- B는 A가 커밋할 때까지 **기다립니다**(6ms → 1016ms). 그래서 정확하지만, 잠금을 오래 쥐면 **다른 요청이 줄줄이 대기**합니다.
- 잠금 중에 외부 API 호출 같은 느린 작업을 하면 안 됩니다. **트랜잭션은 짧게.**
- 여러 행을 잠글 때는 04 문서의 데드락 규칙(**같은 순서로**)이 그대로 적용됩니다.

### 참고 — 낙관적 락 (JPA `@Version`)

충돌이 드문 경우에는 잠그지 않고, **저장할 때 버전 번호로 충돌을 감지**하는 방법도 있습니다.

```sql
UPDATE post SET content = ?, version = version + 1 WHERE id = ? AND version = 3
-- 변경된 행 0 → 누가 먼저 수정함 → "다른 사람이 먼저 수정했습니다" 안내 후 다시 시도
```
JPA에서는 엔티티에 `@Version` 필드를 두면 이 쿼리를 자동으로 만들어 줍니다. 게시글 동시 편집처럼 **충돌이 드물고, 나면 사용자에게 알려도 되는** 곳에 맞습니다.

| 방법 | 언제 | 단점 |
|---|---|---|
| `UPDATE x = x - ?` | 단순 증감 (재고, 잔액, 조회수) | 복잡한 검증은 어려움 |
| `SELECT ... FOR UPDATE` (비관적) | 충돌이 잦고, 반드시 순서대로 처리해야 함 | 대기·데드락 위험 |
| `@Version` (낙관적) | 충돌이 드묾 | 충돌 시 재시도·안내 처리 필요 |

## 4. 인덱스 — 책 뒤의 "찾아보기"

인덱스가 없으면 DB는 원하는 행을 찾으려고 **처음부터 끝까지 전부** 확인합니다(**전체 스캔**, Full Table Scan). 인덱스는 특정 컬럼 값을 **정렬해 둔 별도의 자료구조**(보통 **B-Tree** 계열)로, 책 뒤의 찾아보기처럼 바로 위치를 찾아갑니다.

```
테이블 (입력된 순서)                 email 인덱스 (정렬됨, B-Tree)
┌────┬────────────────────┐          ┌────────────────────────┬──────┐
│ id │ email              │          │ user1@example.com      │ → 1  │
├────┼────────────────────┤          │ user10@example.com     │ → 10 │
│ 1  │ user1@example.com  │          │ user100@example.com    │ → 100│
│ 2  │ user2@example.com  │          │ ...                    │      │
│ ...│ ...                │          │ user250000@example.com │ → 250000 ◀ 정렬돼 있으니
└────┴────────────────────┘          └────────────────────────┴──────┘   몇 단계 만에 찾음
```

- 30만 건이라도 B-Tree는 **몇 단계**만 내려가면 찾습니다(05_algorithm의 **이진 탐색 O(log N)** 과 같은 원리).
- 기본키(PK)에는 인덱스가 **자동으로** 만들어집니다. 그래서 `findById` 는 항상 빠릅니다.

### 🧪 직접 확인 — 30만 건에서 인덱스 유무

```powershell
java -cp "../../../03_Database/샘플/jdbc/lib/h2-2.3.232.jar" "-Dfile.encoding=UTF-8" IndexLab.java
```
```
회원 300,000건 준비 완료 (480ms)

=== 1. 인덱스 없이 email 로 1건 찾기 ===
  실행계획: ❌ 전체 스캔(tableScan)
    SELECT ... FROM "PUBLIC"."MEMBER" /* PUBLIC.MEMBER.tableScan */ WHERE "EMAIL" = 'user250000@example.com'
  user250000@example.com 조회 결과=회원250000 / 서로 다른 회원 100명 조회, 1회 평균 8.592ms

=== 2. email 에 인덱스 만들기 ===
CREATE INDEX 소요 368ms  (인덱스는 공짜가 아니다: 만들 때·INSERT/UPDATE 때마다 비용)
  실행계획: ✅ 인덱스 사용
    SELECT ... FROM "PUBLIC"."MEMBER" /* PUBLIC.IDX_MEMBER_EMAIL: EMAIL = 'user250000@example.com' */ WHERE ...
  user250000@example.com 조회 결과=회원250000 / 서로 다른 회원 100명 조회, 1회 평균 0.060ms
```

**8.6ms → 0.06ms, 약 150배.** 인메모리 DB라 이 정도이고, 실제 디스크 기반 DB에서 데이터가 수천만 건이면 차이는 **초 단위**로 벌어집니다.

> 🔍 **실측하며 겪은 함정**: 처음엔 같은 email로 100번 반복 조회했더니 **인덱스 없이도 0.033ms**로 나왔습니다. H2가 같은 쿼리의 결과를 재사용했기 때문입니다. 그래서 매번 다른 회원을 조회하도록 고쳤습니다. **같은 값으로 반복 측정하면 캐시 때문에 속습니다** — 성능 측정의 기본 함정입니다.

### 인덱스가 있어도 안 쓰이는 경우

```
[앞부분 일치 LIKE 'user25%'] → 정렬된 인덱스에서 범위로 찾을 수 있음
  실행계획: ✅ 인덱스 사용
    /* PUBLIC.IDX_MEMBER_EMAIL: EMAIL >= 'user25' AND EMAIL < 'user26' */
[중간 일치 LIKE '%250000%'] → 어디서 시작할지 모르니 전부 확인
  실행계획: ❌ 전체 스캔(tableScan)
[컬럼에 함수 LOWER(email) = ...] → 인덱스엔 원래 값이 정렬돼 있지 LOWER 결과가 아님
  실행계획: ❌ 전체 스캔(tableScan)
```

H2가 `LIKE 'user25%'` 를 **`>= 'user25' AND < 'user26'` 범위 검색으로 바꾼 것**에 주목하세요. 정렬돼 있으니 시작점을 찾을 수 있는 것입니다. 전화번호부에서 "김"으로 시작하는 사람은 찾기 쉽지만, 이름 **가운데**에 "민"이 들어간 사람은 처음부터 다 봐야 하는 것과 같습니다.

| 인덱스를 못 쓰는 패턴 | 예 | 대안 |
|---|---|---|
| 앞에 `%` 가 붙은 LIKE | `WHERE title LIKE '%공지%'` | 전문 검색(Full-Text) 인덱스, 검색 엔진 |
| 컬럼에 함수·계산 | `WHERE LOWER(email) = ?`, `WHERE YEAR(created_at) = 2026` | 저장할 때 소문자로 통일, `created_at >= '2026-01-01' AND < '2027-01-01'` |
| 타입 불일치 | 문자 컬럼에 숫자로 비교 `WHERE phone = 01012345678` | 타입을 맞춰 바인딩 |
| 복합 인덱스의 앞 컬럼 생략 | 인덱스 `(last_name, first_name)` 인데 `WHERE first_name = ?` 만 | 인덱스 컬럼 순서 = 자주 쓰는 조건 순서 |

### 인덱스는 공짜가 아니다

- **쓰기가 느려집니다.** INSERT·UPDATE·DELETE 때마다 인덱스도 고쳐야 합니다(실측: 30만 건에 인덱스 하나 만드는 데 368ms).
- **저장 공간**을 더 씁니다.
- 그래서 "모든 컬럼에 인덱스"가 아니라, **WHERE·JOIN·ORDER BY에 자주 쓰이고, 값이 다양한(선택도가 높은)** 컬럼에 만듭니다. 성별(M/F)처럼 값이 두세 가지뿐인 컬럼은 효과가 적습니다.

### MySQL에서 실행 계획 보기

```sql
EXPLAIN SELECT * FROM member WHERE email = 'user250000@example.com';
```
- `type` 컬럼이 **`ALL`** 이면 전체 스캔입니다. `ref`, `const`, `range` 면 인덱스를 쓰는 중입니다.
- `key` 컬럼에 사용한 인덱스 이름이 나옵니다.
- 느린 쿼리를 받으면 **추측하지 말고 EXPLAIN부터** 보세요. 자세한 읽는 법은 [MySQL 공식 문서 — EXPLAIN 출력](https://dev.mysql.com/doc/refman/8.4/en/explain-output.html).

## 5. 스프링에서는 — `@Transactional`

스프링에서는 `commit()`/`rollback()` 을 직접 부르지 않고 `@Transactional` 을 붙입니다. 메서드가 정상 종료하면 커밋, **런타임 예외**가 나면 롤백합니다.

```java
@Transactional
public void withdraw(Long accountId, int amount) {
    int updated = accountRepository.decreaseBalance(accountId, amount);  // UPDATE ... balance - ? WHERE ... balance >= ?
    if (updated == 0) throw new IllegalStateException("잔액 부족");        // 런타임 예외 → 롤백
}
```

- `@Transactional` 을 붙여도 **3절의 갱신 분실은 그대로 생깁니다.** 트랜잭션은 원자성을 줄 뿐, 동시 수정 문제는 해결 1·2로 따로 막아야 합니다.
- `@Transactional` 이 **안 먹는** 대표 함정(같은 클래스 안에서 호출)은 07 문서에서 프록시 패턴과 함께 봅니다.

## 6. 함정

| 오해 | 실제 |
|---|---|
| "트랜잭션을 쓰면 동시성 문제가 없다" | 원자성 ≠ 동시성 안전. **읽고-계산하고-쓰기** 패턴은 갱신 분실 |
| "격리 수준을 SERIALIZABLE로 올리면 끝" | 안전하지만 대기·실패가 크게 늘어 성능이 급락. 보통 해결 1·2로 국소적으로 막음 |
| "로컬(H2)에서 확인했으니 운영(MySQL)도 같다" | 기본 격리 수준부터 다름 (READ COMMITTED vs REPEATABLE READ) |
| "인덱스를 만들었으니 빨라진다" | `LIKE '%...'`, 컬럼에 함수 씌우면 안 쓰임. **EXPLAIN으로 확인** |
| "인덱스는 많을수록 좋다" | 쓰기 성능 저하, 공간 증가. 자주 조회하는 조건에만 |
| 같은 쿼리를 반복해 성능 측정 | DB·JVM 캐시 때문에 실제보다 빠르게 나옴. 값을 바꿔 가며 측정 |

---

## ✅ 체크리스트

- [ ] ACID 각각을 예와 함께 말하고, commit/rollback이 그중 무엇인지 안다
- [ ] Dirty Read, Non-Repeatable Read, Phantom Read를 구분할 수 있다
- [ ] MySQL과 H2(그리고 Oracle·PostgreSQL)의 기본 격리 수준을 안다
- [ ] `LostUpdateLab` 으로 갱신 분실을 재현하고, 그것이 04 문서의 레이스 컨디션과 같은 구조임을 설명할 수 있다
- [ ] `UPDATE x = x - ?`, `SELECT ... FOR UPDATE`, `@Version` 을 언제 쓰는지 구분할 수 있다
- [ ] `IndexLab` 으로 인덱스 유무에 따른 실행 계획과 시간 차이를 확인했다
- [ ] 인덱스가 있어도 안 쓰이는 패턴 3가지를 말할 수 있다
- [ ] MySQL `EXPLAIN` 의 `type: ALL` 이 무엇을 뜻하는지 안다
