# 07. 객체지향과 설계 원칙

> 🎯 목표: 객체지향 4대 특성과 SOLID를 **스프링 코드 속에서** 찾아 설명하고, 스프링이 쓰는 디자인 패턴(특히 **프록시**)으로 `@Transactional` 이 안 먹는 이유를 설명한다.

---

## 도입 — 왜 `new IntroService()` 라고 쓰면 안 될까?

[SpringBoot 04 — A5](../Spring/SpringBoot/04_헷갈리기_쉬운_개념.md)에서 "스프링이 객체를 만들어 넣어 준다(DI)"고 배웠습니다. 그런데 **왜** 그렇게 할까요? 직접 `new` 하는 게 더 간단해 보이는데요.

```java
// A: 직접 만든다
public class IntroController {
    private final IntroService service = new IntroService(new JpaIntroRepository());
}

// B: 받아서 쓴다 (스프링 방식)
public class IntroController {
    private final IntroService service;
    public IntroController(IntroService service) { this.service = service; }
}
```

이 문서가 끝나면 B가 왜 나은지, 그리고 그 뒤에 어떤 **설계 원칙**이 있는지 설명할 수 있습니다.

> ⚠️ 이 문서의 원칙은 **"이렇게 해야만 한다"는 법칙이 아니라, 변경을 쉽게 만드는 경험칙**입니다. 작은 프로젝트에 원칙을 과하게 적용하면 오히려 읽기 어려워집니다(6절).

## 1. 객체지향 4대 특성 — 한 줄 정의와 자바 예

| 특성 | 한 줄 정의 | 자바·스프링에서 |
|---|---|---|
| **캡슐화** | 데이터는 숨기고, 정해진 방법(메서드)으로만 바꾸게 함 | `private` 필드 + 검증하는 메서드 |
| **추상화** | 핵심만 드러내고 세부는 감춤 | 인터페이스 `IntroRepository` — "저장한다"만 보이고 JPA인지 MyBatis인지는 숨김 |
| **상속** | 기존 클래스를 물려받아 확장 | `extends`. 스프링에서는 직접 쓸 일이 생각보다 적음 |
| **다형성** | 같은 타입으로 불러도 실제 객체에 따라 다르게 동작 | `PasswordEncoder` 타입 변수에 `BCryptPasswordEncoder` 를 넣어 사용 |

### 캡슐화 — setter를 열어 두면 생기는 일

```java
// ❌ 아무나 아무 값으로 바꿀 수 있음
public class Account {
    private int balance;
    public void setBalance(int balance) { this.balance = balance; }   // -100000 도 들어감
}

// ✅ 규칙을 객체 안에 가둠
public class Account {
    private int balance;
    public void withdraw(int amount) {
        if (amount <= 0) throw new IllegalArgumentException("출금액은 0보다 커야 합니다");
        if (balance < amount) throw new IllegalStateException("잔액 부족");
        this.balance -= amount;
    }
}
```

- 규칙("잔액은 음수가 될 수 없다")이 **한 곳**에 있으니, 출금하는 코드가 100군데여도 규칙이 깨지지 않습니다.
- 엔티티에 무심코 `@Setter`(Lombok)를 붙이기 전에 한 번 생각해 보세요.

### 다형성 — `if` 문을 객체로 바꾸기

```java
// ❌ 결제 수단이 늘 때마다 이 메서드를 고쳐야 함
if (type.equals("CARD")) { ... } else if (type.equals("KAKAO")) { ... } else if ...

// ✅ 인터페이스 하나, 구현체 여러 개
public interface PaymentMethod { void pay(int amount); }
public class CardPayment implements PaymentMethod { ... }
public class KakaoPayment implements PaymentMethod { ... }

paymentMethod.pay(amount);   // 어떤 구현체인지 몰라도 됨
```

## 2. SOLID — 다섯 가지 설계 원칙

| 원칙 | 한 줄 요약 | 스프링·실무에서의 모습 |
|---|---|---|
| **S** 단일 책임 (SRP) | 클래스를 바꿀 **이유는 하나**여야 한다 | Controller(요청·응답) / Service(업무 규칙) / Repository(저장) 계층 분리 |
| **O** 개방-폐쇄 (OCP) | 확장에는 열려 있고, 수정에는 닫혀 있게 | 결제 수단 추가 = 구현체 **추가**, 기존 코드 **수정 없음** |
| **L** 리스코프 치환 (LSP) | 자식은 부모 자리에 넣어도 **약속대로** 동작해야 한다 | `PasswordEncoder` 구현체는 무엇이든 `matches()` 가 올바르게 동작해야 함 |
| **I** 인터페이스 분리 (ISP) | 안 쓰는 메서드에 의존하게 만들지 말 것 | 거대한 `CommonService` 하나보다 역할별 작은 인터페이스 |
| **D** 의존 역전 (DIP) | 구체 클래스가 아니라 **추상(인터페이스)** 에 의존 | Service는 `JpaIntroRepository` 가 아니라 `IntroRepository` 인터페이스에 의존 |

### SRP — "바꿀 이유"로 판단하기

```java
// ❌ 이 클래스를 바꿀 이유: 화면 변경, 할인 정책 변경, DB 변경, 메일 문구 변경 ...
public class OrderController {
    @PostMapping("/orders")
    public String order(...) {
        // 요청 검증 + 가격 계산 + 할인 + SQL 직접 실행 + 메일 발송 + 화면 선택 (300줄)
    }
}
```

계층을 나누는 이유가 바로 이것입니다. 할인 정책이 바뀌면 Service만, DB가 바뀌면 Repository만 고칩니다.

### DIP + DI — 도입부 질문의 답

```
❌ A: Controller → (직접 new) → IntroService → (직접 new) → JpaIntroRepository
      MyBatis로 바꾸려면? Service 코드를 열어서 고쳐야 함
      테스트하려면? 진짜 DB가 있어야 함

✅ B: Controller → IntroService(인터페이스 or 클래스) → IntroRepository(인터페이스)
                                                          ▲            ▲
                                              JpaIntroRepository  MyBatisIntroRepository
      누구를 넣을지는 스프링(조립 담당)이 결정 → Service 코드는 그대로
      테스트할 땐 가짜(Mock) Repository를 넣으면 됨
```

- **DIP(원칙)**: 구체 클래스 말고 인터페이스에 의존하라.
- **DI(기술)**: 의존할 객체를 밖에서 넣어 주는 방법. 스프링 컨테이너가 이 조립을 해 줍니다.
- [Spring/Database 03 — JPA vs MyBatis](../Spring/Database/03_JPA_vs_MyBatis.md)에서 같은 기능을 두 방식으로 구현할 수 있었던 것, [Testing](../Spring/Testing/README.md)에서 Mock을 넣어 테스트할 수 있었던 것이 모두 이 덕분입니다.

### 상속보다 조합(Composition)

```java
// ❌ 기능을 얻으려고 상속: 부모가 바뀌면 자식이 줄줄이 깨짐, 자바는 하나만 상속 가능
public class OrderService extends LoggingService { ... }

// ✅ 필요한 기능을 가진 객체를 필드로 받아서 사용
public class OrderService {
    private final AuditLogger auditLogger;   // 주입받음
}
```

상속은 "**A는 B의 한 종류다**(is-a)"가 확실할 때만 씁니다. 코드 재사용이 목적이면 조합을 먼저 고려하세요.

## 3. 스프링 안에 숨은 디자인 패턴

디자인 패턴은 "자주 나오는 설계 문제에 붙인 이름"입니다. 외우기보다 **이미 쓰고 있는 코드에서 알아보는 것**이 먼저입니다.

| 패턴 | 한 줄 정의 | 스프링에서 |
|---|---|---|
| **싱글톤** | 객체를 하나만 만들어 공유 | 스프링 빈의 기본 스코프. 그래서 **상태를 두면 안 됨**(04 문서) |
| **프록시** | 진짜 객체 앞에 대리인을 세워 부가 기능 수행 | `@Transactional`, `@Async`, Spring Security 메서드 보안 |
| **템플릿 메서드** | 전체 흐름은 고정, 바뀌는 부분만 끼워 넣음 | `JdbcTemplate`: 연결·예외·자원 반납은 고정, SQL과 결과 매핑만 우리가 작성 |
| **전략** | 알고리즘을 인터페이스로 갈아 끼움 | `PasswordEncoder`, 결제 수단 예시 |
| **팩토리** | 객체 생성을 전담 | 스프링 컨테이너(`BeanFactory`) 자체 |
| **옵저버** | 일이 생기면 구독자들에게 알림 | `ApplicationEventPublisher` + `@EventListener` (회원가입 후 메일 발송 분리) |

### 프록시 — `@Transactional` 은 어떻게 동작할까

스프링은 `@Transactional` 이 붙은 빈을 그대로 주입하지 않고, **앞에 프록시(대리인)를 세워** 주입합니다.

```
Controller ──호출──▶ [프록시 OrderService] ──▶ [진짜 OrderService]
                      │ 1. 트랜잭션 시작
                      │ 2. 진짜 메서드 호출 ─────────▶ order() 실행
                      │ 3. 정상이면 커밋 / 예외면 롤백
```

### ⚠️ 그래서 생기는 단골 함정 — 같은 클래스 안에서 호출

```java
@Service
public class OrderService {

    public void placeOrder(OrderRequest req) {
        // ... 검증 ...
        saveOrder(req);                 // ❌ this.saveOrder() — 프록시를 거치지 않음!
    }

    @Transactional
    public void saveOrder(OrderRequest req) {
        orderRepository.save(...);
        stockRepository.decrease(...);  // 여기서 예외가 나도 앞의 save가 롤백되지 않음
    }
}
```

- Controller가 `placeOrder()` 를 부를 때는 프록시를 거치지만, `placeOrder()` 안에서 `saveOrder()` 를 부르는 건 **진짜 객체가 자기 자신(`this`)을 직접 호출**하는 것이라 프록시를 건너뜁니다.
- 결과: `@Transactional` 이 **조용히 무시**됩니다. 에러도 경고도 없습니다.
- 해결: 트랜잭션이 필요한 메서드를 **바깥에서 호출되는 메서드**(`placeOrder`)에 붙이거나, 별도 빈으로 분리합니다.
- 같은 이유로 `private` 메서드에 붙인 `@Transactional` 도 동작하지 않습니다.

> 💡 "어노테이션을 붙였는데 안 먹어요"(`@Transactional`, `@Async`, `@Cacheable`)의 상당수는 이 **프록시 자기 호출** 문제입니다. 스프링의 마법은 대부분 프록시라는 것을 기억하세요.

### 템플릿 메서드 — 03_Database JDBC 코드와 비교

[03_Database의 JDBC 실습](../03_Database/04_JDBC_실습.md)에서는 `Connection` 열기 → `PreparedStatement` → `ResultSet` 순회 → `close` 를 매번 직접 썼습니다. `JdbcTemplate` 은 이 **고정된 흐름**을 대신하고, 우리는 **바뀌는 부분**(SQL, 한 행을 객체로 바꾸는 방법)만 넘깁니다.

```java
List<Intro> list = jdbcTemplate.query(
        "SELECT id, name FROM intro",                                   // 바뀌는 부분 ①
        (rs, rowNum) -> new Intro(rs.getLong("id"), rs.getString("name"))  // 바뀌는 부분 ②
);
// 연결·예외 변환·자원 반납은 JdbcTemplate이 알아서
```

## 4. 좋은 설계인지 확인하는 질문 세 가지

원칙 이름보다 이 질문이 실무에서 더 쓸모 있습니다.

1. **"이 요구사항이 바뀌면 몇 개의 파일을 고쳐야 하나?"** — 많으면 책임이 흩어져 있음 (SRP)
2. **"이 클래스를 진짜 DB·외부 API 없이 테스트할 수 있나?"** — 못 하면 구체 클래스에 묶여 있음 (DIP)
3. **"새 종류(결제 수단, 알림 채널)를 추가할 때 기존 `if` 문을 고쳐야 하나?"** — 그렇다면 다형성 후보 (OCP)

[SpringBoot intro](../Spring/SpringBoot/README.md) 또는 [Capstone](../Spring/Capstone/README.md) 프로젝트를 열고 확인해 보세요.

- [ ] Controller에 업무 규칙(계산, 검증 로직)이 들어 있지 않은가? → Service로
- [ ] 엔티티에 `@Setter` 가 열려 있는가? → 의미 있는 메서드(`changeName`, `withdraw`)로
- [ ] `@Transactional` 메서드를 같은 클래스 안에서 호출하는 곳이 있는가?
- [ ] `@Service` 에 `final` 이 아닌 필드가 있는가? (04 문서)

## 6. 함정 — 원칙의 과잉 적용

| 과잉 적용 | 문제 | 기준 |
|---|---|---|
| 구현체가 하나뿐이고 바뀔 계획도 없는데 모든 Service에 `XxxService` + `XxxServiceImpl` | 파일만 두 배, 따라가기 어려움 | **바뀔 가능성이 실제로 있거나 테스트에 필요할 때** 인터페이스 도입 (전자정부프레임워크 관례는 `ServiceImpl` 을 쓰므로 프로젝트 관례가 우선) |
| 두 번 쓰일까 봐 미리 만든 공통 모듈, 추상 클래스 | 아무도 안 쓰는 확장 지점, 수정이 오히려 어려움 | **세 번 반복되면** 그때 추출 |
| 패턴 이름을 붙이려고 패턴을 씀 | 단순한 `if` 두 개를 클래스 다섯 개로 | 패턴은 문제가 있을 때 해결책으로 |

> 💡 **"지금 필요하지 않은 것은 만들지 않는다"(YAGNI)** 도 설계 원칙입니다. 유지보수 현장에서는 원칙을 많이 아는 사람보다, **기존 코드의 관례를 따르면서 변경 범위를 작게** 만드는 사람이 신뢰받습니다([eGovFrame 브릿지](../Spring/eGovFrame-Bridge/README.md)).

## ✅ 체크리스트

- [ ] 객체지향 4대 특성을 한 줄씩, 자바 예와 함께 말할 수 있다
- [ ] setter 대신 의미 있는 메서드를 두는 이유(캡슐화)를 설명할 수 있다
- [ ] SOLID 다섯 가지를 스프링 코드의 예로 하나씩 말할 수 있다
- [ ] DIP와 DI의 차이, 그리고 `new` 대신 주입받는 이유를 설명할 수 있다
- [ ] 스프링에서 싱글톤·프록시·템플릿 메서드·전략 패턴이 쓰이는 곳을 하나씩 말할 수 있다
- [ ] `@Transactional` 이 같은 클래스 내부 호출에서 동작하지 않는 이유를 프록시로 설명할 수 있다
- [ ] 원칙을 과하게 적용했을 때의 문제를 예로 들 수 있다
