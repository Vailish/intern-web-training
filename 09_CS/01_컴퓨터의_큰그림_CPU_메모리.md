# 01. 컴퓨터의 큰 그림 — CPU와 메모리

> 🎯 목표: CPU·메모리·디스크·네트워크의 **속도 차이를 자릿수로** 말할 수 있고, 그 차이 때문에 "반복문 안의 DB 호출"이 왜 가장 흔한 성능 문제인지 설명한다.

---

## 도입 — 똑같은 계산인데 왜 28배 차이가 날까?

4096 × 4096 크기의 2차원 배열에서 모든 칸을 더합니다. 두 코드의 차이는 **반복문 두 줄의 순서**뿐입니다.

```java
// A: 행 방향 (옆으로)              // B: 열 방향 (아래로)
for (int i = 0; i < N; i++)        for (int j = 0; j < N; j++)
    for (int j = 0; j < N; j++)        for (int i = 0; i < N; i++)
        sum += g[i][j];                    sum += g[i][j];
```

덧셈 횟수는 똑같이 약 1,677만 번입니다. 실제로 돌려 보면:

```
1회차  행 방향    4ms   열 방향  111ms   (약 27.8배)  합계 확인 true
```

계산량이 같은데 왜 이렇게 다를까요? 답은 **"데이터가 CPU에서 얼마나 멀리 있느냐"** 입니다. 이 문서가 끝나면 이 질문에 답할 수 있습니다.

---

## 1. 컴퓨터의 네 부품 — 식당으로 비유하면

| 부품 | 하는 일 | 식당 비유 | 특징 |
|---|---|---|---|
| **CPU** | 계산, 명령 실행 | 요리사 | 엄청 빠름. 손에 든 것(레지스터)과 도마 위(캐시)만 바로 쓸 수 있음 |
| **메모리 (RAM)** | 실행 중인 프로그램과 데이터 보관 | 주방 냉장고 | 빠르지만 **전원이 꺼지면 사라짐** |
| **저장장치 (SSD/HDD)** | 파일, DB 데이터 영구 보관 | 건물 지하 창고 | 크고 영구적이지만 느림 |
| **네트워크** | 다른 컴퓨터와 통신 | 다른 동네 시장 | 가장 느림. 상대가 바쁘거나 길이 막힐 수도 있음 |

- 프로그램을 실행하면 디스크에 있던 코드와 데이터가 **메모리로 올라오고**, CPU는 메모리에서 꺼내 계산합니다.
- 스프링 앱이 DB를 조회하면 → **네트워크**를 타고 DB 서버로 가서 → DB 서버가 **디스크나 메모리**에서 찾아 → 다시 네트워크로 돌아옵니다.

---

## 2. 메모리 계층 — 속도 차이는 "자릿수"로 기억하라

CPU가 1초에 수십억 번 계산하는 동안, 데이터를 가져오는 시간은 위치에 따라 **수백만 배**까지 차이 납니다.

| 위치 | 대략적인 시간 | 1ns를 **1초**로 늘려 보면 |
|---|---|---|
| CPU 캐시 (L1) | 약 1ns | 1초 |
| 메인 메모리 (RAM) | 약 100ns | 약 1분 40초 |
| SSD에서 임의 위치 읽기 | 약 100µs (0.1ms) | 약 1일 |
| 같은 데이터센터 안 서버 왕복 | 약 0.5ms | 약 6일 |
| HDD 탐색 | 약 10ms | 약 4개월 |
| 한국 ↔ 미국 서버 왕복 | 약 150ms | 약 5년 |

> ⚠️ **숫자의 출처와 한계**: Google의 Jeff Dean, Peter Norvig 등이 정리해 널리 알려진 "프로그래머가 알아야 할 지연 시간" 표를 바탕으로 한 **대략적인 자릿수**입니다(2차 자료). 하드웨어 세대마다 값은 달라지지만, **"캐시 ≪ 메모리 ≪ 디스크 ≪ 네트워크"라는 순서와 자릿수 차이**는 수십 년째 그대로입니다. 정확한 값을 외우지 말고 이 순서를 기억하세요.

---

## 3. 캐시 — CPU는 메모리를 "덩어리"로 가져온다

CPU는 메모리에서 값 하나만 가져오지 않습니다. 주변 데이터를 **한 덩어리(캐시 라인, 보통 64바이트)** 로 가져와 캐시에 둡니다. "방금 쓴 것 근처를 곧 또 쓸 것"이라고 예측하는 것이죠(**지역성**, locality).

```
메모리 속 2차원 배열 (자바는 행마다 별도 배열)
 g[0] → [ 1 | 1 | 1 | 1 | 1 | ... ]   ← 행 방향: 옆 칸이 이미 캐시에 있음 (캐시 적중)
 g[1] → [ 1 | 1 | 1 | 1 | 1 | ... ]
 g[2] → [ 1 | 1 | 1 | 1 | 1 | ... ]   ← 열 방향: 매번 다른 행으로 점프 → 캐시에 없음 (캐시 미스)
```

- **행 방향**: 한 번 가져온 덩어리 안에서 다음 값을 바로 꺼냄 → 빠름
- **열 방향**: 매번 멀리 떨어진 메모리로 점프 → 매번 RAM까지 다녀옴 → 느림

## 4. 웹 개발자에게 이게 왜 중요한가

웹 개발자가 CPU 캐시를 직접 튜닝할 일은 거의 없습니다. 하지만 **같은 원리가 한 단계 위에서 그대로 반복**됩니다.

| CPU 수준 | 웹 서비스 수준 |
|---|---|
| 캐시는 빠르고 RAM은 느리다 | **앱 메모리(캐시)** 는 빠르고 **DB**는 느리다 |
| 덩어리로 가져오면 효율적 | **한 번에 모아서** 조회·저장하면 효율적 (배치, `IN` 조회) |
| 캐시 미스가 쌓이면 느려짐 | **DB 왕복**이 쌓이면 느려짐 |

### 가장 흔한 실수 — 반복문 안의 DB 호출 (N+1 문제)

```java
// ❌ 게시글 100개를 가져온 뒤, 글마다 작성자를 따로 조회 → DB 왕복 1 + 100 = 101번
List<Post> posts = postRepository.findAll();          // 1번
for (Post p : posts) {
    Member writer = memberRepository.findById(p.getWriterId()).orElseThrow();  // 100번
}
```

- 쿼리 하나는 1ms라도 **왕복 101번이면 100ms 이상**. 데이터가 1만 건이면 1만 번.
- 해결 방향: `JOIN` 으로 한 번에 가져오기, 작성자 ID를 모아 `WHERE id IN (...)` 으로 한 번에 조회.
- JPA를 쓰면 이 문제가 **코드에 안 보이게** 숨어서 생기기 쉽습니다(연관관계 지연 로딩). 이름이 붙을 만큼 흔해서 **"N+1 문제"** 라고 부릅니다.

> 💡 실무 성능 문제의 1순위는 알고리즘(O(N²))보다 **불필요한 DB·네트워크 왕복**인 경우가 많습니다. 느린 API를 만나면 먼저 "요청 한 번에 쿼리가 몇 번 나가나?"를 세어 보세요. 스프링에서는 SQL 로그(`spring.jpa.show-sql=true`)를 켜면 셀 수 있습니다.

같은 이유로 06 문서의 `IndexLab` 은 30만 건을 넣을 때 1건씩 보내지 않고 **1만 건씩 묶어서(batch)** 보냅니다.

## 5. 비트와 바이트, 2진수와 16진수

컴퓨터는 모든 것을 0과 1로 저장합니다. 이 단위를 알아야 02 문서(숫자·문자)와 07_Network의 패킷 해부가 읽힙니다.

| 용어 | 뜻 | 예 |
|---|---|---|
| **비트 (bit)** | 0 또는 1 하나 | |
| **바이트 (byte)** | 8비트. 저장의 기본 단위 | 0 ~ 255 표현 가능 (2⁸ = 256가지) |
| **16진수 (hex)** | 0~9, A~F. **16진수 2자리 = 1바이트** | `EA B0 80` = 3바이트 (= UTF-8의 "가") |
| `int` | 자바에서 32비트 = 4바이트 | 약 ±21억 |
| `long` | 64비트 = 8바이트 | 약 ±922경 |

### 헷갈리기 쉬운 단위 두 가지

| 상황 | 주의할 점 |
|---|---|
| **인터넷 속도 1Gbps** | 소문자 **b = bit**. 바이트로 바꾸면 ÷8 → 약 **125MB/s**. "1기가 인터넷인데 왜 125MB밖에 안 나와요?"의 답 |
| **디스크 1TB가 931GB로 보임** | 제조사는 1KB = 1,000바이트, Windows는 1KB = 1,024바이트로 계산해서 생기는 차이. 정확히 구분할 땐 1,024 단위를 **KiB, MiB, GiB** 로 씀 |

## 6. 자바 코드는 어떻게 CPU까지 가나 — JVM과 JIT

CPU는 자바를 모릅니다. CPU가 아는 것은 **기계어**뿐입니다.

```
Hello.java ──javac(컴파일)──▶ Hello.class (바이트코드) ──JVM──▶ 기계어 ──▶ CPU
                                    │
                                    └ Windows든 리눅스든 같은 .class 파일이 돈다
                                      (JVM이 OS마다 따로 있어서)
```

- **바이트코드**: JVM을 위한 중간 언어. 그래서 Windows에서 빌드한 jar를 리눅스 서버(Docker)에서 그대로 실행할 수 있었습니다([06_Deploy](../06_Deploy/README.md)).
- **JIT 컴파일러**: JVM은 처음엔 바이트코드를 한 줄씩 해석하다가, **자주 실행되는 코드를 실행 도중 기계어로 번역**해 빠르게 만듭니다.
  - 그래서 자바 앱은 **켜자마자는 느리고, 조금 지나면 빨라집니다(워밍업)**. 성능을 잴 때 첫 측정을 버리는 이유입니다. `CacheLab` 도 측정 전에 두 번 먼저 돌립니다.
  - JIT는 코드를 과감하게 최적화하기도 합니다. 04 문서에서 이 최적화 때문에 동시성 버그가 **숨어 버리는** 장면을 봅니다.

> `java X.java` 로 소스 파일을 바로 실행하는 것도 내부적으로는 **메모리 안에서 javac로 컴파일한 뒤 실행**하는 것입니다.

## 7. 함정

| 오해 | 실제 |
|---|---|
| "메모리는 빠르니까 몇 번 더 읽어도 상관없다" | CPU 기준으로 RAM은 캐시보다 약 100배 느림. 다만 웹 개발에서 이 차이보다 **DB·네트워크 왕복이 수천 배 더 크다**는 게 핵심 |
| "쿼리 하나에 1ms면 빠른 거다" | 반복문 안에 있으면 1ms × N. **횟수**를 봐야 함 |
| "1Gbps = 1GB/s" | bit와 byte는 8배 차이 |
| 성능을 한 번만 재고 결론 냄 | 자바는 JIT 워밍업 때문에 첫 실행이 느림. 여러 번 재서 경향을 보기 |
