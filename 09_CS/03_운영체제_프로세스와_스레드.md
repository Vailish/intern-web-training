# 03. 운영체제 — 프로세스와 스레드

> 🎯 목표: 프로그램·프로세스·스레드의 차이를 메모리 그림으로 설명하고, **톰캣이 요청을 스레드 풀로 처리하는 방식**과 그 때문에 생기는 "응답 지연"을 설명한다.

---

## 도입 — `@Service` 객체는 1개인데, 사용자 100명은 어떻게 동시에 쓰지?

스프링에서 `IntroService` 는 앱 전체에 **딱 1개**만 만들어집니다(싱글톤). 그런데 사용자 100명이 동시에 자기소개서 목록을 열면, 100명 모두 응답을 받습니다.

- 객체가 1개인데 어떻게 100명을 동시에 처리할까요?
- 100명이 아니라 1만 명이 오면 어떻게 될까요?

답은 **스레드**입니다. 그리고 이 구조 때문에 04 문서의 동시성 버그가 생깁니다.

---

## 1. 프로그램 · 프로세스 · 스레드

| 용어 | 뜻 | 비유 |
|---|---|---|
| **프로그램** | 디스크에 저장된 실행 파일 (`intro.jar`) | 요리책 |
| **프로세스** | 실행 중인 프로그램. **OS가 메모리를 따로 떼어 줌** | 요리책을 펼쳐 놓은 주방 하나 |
| **스레드** | 프로세스 안에서 실제로 코드를 실행하는 흐름 | 그 주방에서 일하는 요리사들 |

- `java -jar intro.jar` 를 실행하면 **프로세스 1개**가 생깁니다. 그 안에서 톰캣이 **스레드 여러 개**를 만들어 요청을 나눠 처리합니다.
- 프로세스끼리는 메모리가 **분리**돼 있습니다. 앱 A가 죽어도 앱 B는 멀쩡합니다.
- 스레드끼리는 같은 프로세스의 메모리(힙)를 **공유**합니다. 빠르게 협력할 수 있지만, **서로의 데이터를 망가뜨릴 수도 있습니다.**

### 프로세스의 메모리 구조

```
┌──────────────── 프로세스 1개 (java -jar intro.jar) ────────────────┐
│                                                                    │
│  코드 영역   : 실행할 코드 (클래스 정보)                    ← 공유   │
│  힙 (Heap)   : new 로 만든 객체 — IntroService, 엔티티...   ← 공유 ⚠️│
│                                                                    │
│  ┌─ 스레드1 스택 ─┐  ┌─ 스레드2 스택 ─┐  ┌─ 스레드3 스택 ─┐          │
│  │ 지역 변수      │  │ 지역 변수      │  │ 지역 변수      │ ← 각자   │
│  │ 메서드 호출 칸 │  │ 메서드 호출 칸 │  │ 메서드 호출 칸 │   따로   │
│  └────────────────┘  └────────────────┘  └────────────────┘          │
└────────────────────────────────────────────────────────────────────┘
```

> 💡 **이 그림 하나가 04 문서 전체의 열쇠입니다.**
> - **지역 변수**는 스레드마다 자기 스택에 따로 있음 → 안전
> - **객체의 필드**는 힙에 있어서 모든 스레드가 같이 봄 → 위험

## 2. CPU 코어와 스레드 — 동시성 vs 병렬성

CPU 코어 하나는 한순간에 스레드 하나만 실행합니다. 그런데 우리 PC에서는 스레드가 수천 개 돌고 있습니다(작업 관리자 → 성능 탭에서 확인해 보세요). 어떻게 가능할까요?

| 개념 | 뜻 | 비유 |
|---|---|---|
| **동시성 (Concurrency)** | 코어 하나가 여러 스레드를 **아주 빠르게 번갈아** 실행 → 동시에 도는 것처럼 보임 | 요리사 1명이 냄비 3개를 오가며 요리 |
| **병렬성 (Parallelism)** | 코어 여러 개가 **실제로 동시에** 실행 | 요리사 3명이 각자 요리 |
| **문맥 교환 (Context Switch)** | 스레드를 바꿀 때 지금까지의 작업 상태를 저장하고 다음 스레드의 상태를 불러오는 일 | 냄비를 바꿀 때마다 레시피 어디까지 했는지 메모하고 다시 읽기 |

- 문맥 교환은 **공짜가 아닙니다.** 스레드가 너무 많으면 실제 일보다 "번갈아 바꾸는 일"에 시간을 더 씁니다.
- 실습 PC의 코어 수는 `Runtime.getRuntime().availableProcessors()` 로 확인할 수 있습니다(04 문서의 `RaceConditionLab` 첫 줄에 출력됨).

### 스레드가 기다리는 시간

웹 요청을 처리하는 스레드는 대부분의 시간을 **계산이 아니라 기다리는 데** 씁니다.

```
요청 처리 1건 (예: 100ms)
├─ 요청 파싱, 비즈니스 로직 ........ 약 2ms   ← CPU 사용
├─ DB 응답 기다림 .................. 약 60ms  ← CPU 안 씀, 스레드는 붙잡혀 있음
├─ 외부 API 응답 기다림 ............ 약 35ms  ← CPU 안 씀, 스레드는 붙잡혀 있음
└─ JSON 변환, 응답 전송 ............ 약 3ms   ← CPU 사용
```

그래서 웹 서버는 코어 수보다 **훨씬 많은 스레드**(수백 개)를 둡니다. 한 스레드가 DB를 기다리는 동안 다른 스레드가 CPU를 쓰면 되니까요.

## 3. 톰캣의 요청 처리 — 스레드 풀

요청이 올 때마다 스레드를 새로 만들고 버리면 느립니다(스레드 생성은 OS 작업이라 비쌈). 그래서 톰캣은 **스레드를 미리 만들어 두고 빌려줬다 돌려받습니다.** 이것이 **스레드 풀**입니다.

```
                     ┌──────────── 톰캣 스레드 풀 (기본 최대 200개) ────────────┐
요청 ──▶ [연결 수락] ─▶│ http-nio-8080-exec-1  ── 처리 중 (DB 기다리는 중)        │
요청 ──▶             ─▶│ http-nio-8080-exec-2  ── 처리 중                          │
요청 ──▶             ─▶│ ...                                                      │
요청 ──▶             ─▶│ http-nio-8080-exec-200 ── 처리 중                         │
                     └─────────────────────────────────────────────────────────────┘
요청 ──▶ [대기열] ── 스레드가 모두 바쁘면 여기서 기다림 → 오래 기다리면 클라이언트 타임아웃
```

스프링부트 4.1 내장 톰캣의 기본값 (`spring-boot-tomcat` 4.1.0 설정 메타데이터에서 확인):

| 설정 | 기본값 | 뜻 |
|---|---|---|
| `server.tomcat.threads.max` | **200** | 동시에 요청을 처리하는 최대 스레드 수 |
| `server.tomcat.threads.min-spare` | 10 | 한가할 때도 유지하는 최소 스레드 수 |
| `server.tomcat.max-connections` | 8192 | 동시에 붙잡아 둘 수 있는 최대 연결 수 |
| `server.tomcat.accept-count` | 100 | 연결이 꽉 찼을 때 OS 대기열 길이 |

> 스프링 앱 로그나 에러 스택에서 `http-nio-8080-exec-3` 같은 스레드 이름을 본 적 있을 겁니다. 그게 톰캣 스레드 풀의 스레드입니다.

### 🧪 직접 실행해 보기 — 스레드가 부족하면?

요청 하나 처리에 1초 걸리는 상황에서, 스레드 2개로 요청 6개를 받습니다.

```powershell
java "-Dfile.encoding=UTF-8" ThreadPoolLab.java
```
```
스레드 풀 크기 2, 요청 6개 (요청 하나 처리에 1초)

요청1  처리 스레드=pool-1-thread-1  대기    1ms + 처리 1000ms = 응답 1002ms
요청2  처리 스레드=pool-1-thread-2  대기    0ms + 처리 1000ms = 응답 1008ms
요청3  처리 스레드=pool-1-thread-1  대기 1002ms + 처리 1000ms = 응답 2015ms
요청4  처리 스레드=pool-1-thread-2  대기 1008ms + 처리 1000ms = 응답 2015ms
요청5  처리 스레드=pool-1-thread-1  대기 2015ms + 처리 1000ms = 응답 3030ms
요청6  처리 스레드=pool-1-thread-2  대기 2015ms + 처리 1000ms = 응답 3030ms

전체 소요 3033ms
```

스레드를 6개로 늘리면:
```powershell
java "-Dfile.encoding=UTF-8" ThreadPoolLab.java 6
```
```
요청6  처리 스레드=pool-1-thread-6  대기    0ms + 처리 1000ms = 응답 1009ms
전체 소요 1011ms
```

관찰할 것:
1. **처리 시간은 늘 1초**인데, 스레드가 부족하면 **대기 시간**이 쌓여 응답이 3초가 됩니다. 사용자는 대기까지 합쳐서 "느리다"고 느낍니다.
2. 스레드 이름 `thread-1`, `thread-2` 가 **재사용**됩니다. 빌려 쓰고 돌려주는 것입니다.

## 4. 실무 연결 — 느린 외부 API 하나가 서버 전체를 멈추는 이유

[External-API](../Spring/External-API/README.md)에서 외부 API에 **타임아웃**을 꼭 설정하라고 배웠습니다. 이제 그 이유를 스레드로 설명할 수 있습니다.

```
외부 API가 응답 없이 멈춤 (타임아웃 설정 없음)
→ 그 API를 부르는 요청의 스레드가 계속 붙잡힘
→ 요청이 계속 들어오면 200개 스레드가 전부 붙잡힘
→ 외부 API와 상관없는 페이지(로그인, 메인)까지 대기열에서 기다림
→ "서버가 죽었다"
```

| 증상 | 의심할 것 |
|---|---|
| 특정 시간대에 모든 페이지가 같이 느려짐 | 스레드 풀 고갈. 느린 쿼리·외부 호출이 스레드를 붙잡고 있는지 |
| CPU는 한가한데 응답이 느림 | 스레드가 **기다리는 중** (DB 커넥션, 외부 API, 잠금) |
| CPU가 100%이고 느림 | 실제 계산이 많음 (무한 루프, 비효율 알고리즘, 과도한 GC → 05 문서) |

> 💡 **"스레드를 1,000개로 늘리면 되지 않나요?"** — 스레드마다 스택 메모리가 필요하고, 문맥 교환 비용이 커지고, 결국 **뒤쪽의 DB 커넥션 풀**(기본 10개 안팎)에서 다시 줄을 섭니다. 병목은 옮겨질 뿐입니다. 먼저 **왜 오래 붙잡히는지**를 고쳐야 합니다.

### 참고 — 가상 스레드 (Java 21+)

Java 21부터 **가상 스레드**가 정식 기능이 됐습니다. OS 스레드보다 훨씬 가벼워서, 기다리는 동안 OS 스레드를 놓아줍니다. 스프링부트에서는 `spring.threads.virtual.enabled=true` 로 켤 수 있습니다(기본값 false). 이 교육과정은 Java 17 기준이라 실습하지 않지만, 면접에서 "요즘 트렌드"로 나올 수 있으니 이름과 목적은 알아 두세요.

## 5. 내 PC에서 프로세스와 스레드 보기

스프링 앱을 실행한 상태에서 해 보세요.

```powershell
jps -l                        # 실행 중인 자바 프로세스와 PID 목록
jcmd <PID> Thread.print       # 그 프로세스의 모든 스레드와 지금 실행 중인 코드
```

- `jcmd` 출력에서 `http-nio-8080-exec-` 로 시작하는 스레드를 찾아보세요. 요청이 없으면 `WAITING` 또는 `TIMED_WAITING` (일감을 기다리는 중) 상태입니다. 앱을 막 켠 직후라면 `min-spare` 값(10)만큼만 만들어져 있는 것도 확인해 보세요.
- 이 "스레드 덤프"는 운영에서 서버가 멈췄을 때 **가장 먼저 뜨는 진단 자료**입니다. 04 문서에서 데드락을 찾을 때 다시 씁니다.
- 작업 관리자 → 세부 정보 탭에서 `java.exe` 의 PID가 `jps` 결과와 같은지 확인해 보세요.

> 🐳 [06_Deploy](../06_Deploy/README.md)의 **컨테이너도 결국 OS 위의 프로세스**입니다. 다만 OS가 파일·네트워크·프로세스 목록을 따로 보이게 격리해 줘서, 컨테이너 안에서는 자기만 있는 것처럼 보입니다.

## 6. 함정

| 오해 | 실제 |
|---|---|
| "싱글톤이면 한 번에 한 요청만 처리한다" | 객체는 1개지만 **스레드 수백 개가 동시에** 그 객체의 메서드를 호출함 |
| "스레드를 늘리면 빨라진다" | 기다리는 원인(느린 쿼리·외부 API)이 그대로면 병목이 옮겨갈 뿐 |
| "CPU 사용률이 낮으니 서버는 여유 있다" | 스레드가 모두 **기다리는 중**이면 CPU는 한가해도 새 요청을 못 받음 |
| "프로세스와 스레드는 비슷한 거다" | 프로세스는 메모리 **분리**, 스레드는 메모리(힙) **공유**. 이 차이가 안전성과 동시성 버그를 가름 |

## ✅ 체크리스트

- [ ] `jps` 와 `jcmd <PID> Thread.print` 로 스프링 앱의 톰캣 스레드를 직접 봤다
