# 05. JVM 메모리와 GC

> 🎯 목표: 스택과 힙에 무엇이 저장되는지 그림으로 설명하고, `StackOverflowError` 와 `OutOfMemoryError` 를 **직접 일으켜** 원인을 구분하며, GC가 "무엇을 못 치우는지" 말할 수 있다.

---

## 도입 — 두 에러는 어디가 넘친 걸까?

```
java.lang.StackOverflowError
	at com.example.intro.Intro.toString(Intro.java:42)
	at com.example.intro.Member.toString(Member.java:31)
	at com.example.intro.Intro.toString(Intro.java:42)
	...

java.lang.OutOfMemoryError: Java heap space
```

둘 다 "메모리가 넘쳤다"는 뜻이지만, **넘친 곳이 다르고 원인도 완전히 다릅니다.** 앞의 것은 코드 몇 줄을 고치면 되고, 뒤의 것은 메모리를 붙잡고 있는 범인을 찾아야 합니다.

---

## 1. JVM 메모리 구조 — 스택과 힙

03 문서의 프로세스 그림을 JVM 기준으로 다시 그리면:

```
┌──────────────────────────── JVM (자바 프로세스) ─────────────────────────────┐
│                                                                             │
│  힙 (Heap) — 모든 스레드가 공유, GC가 관리                                    │
│   ┌──────────────────────────────┐   ┌──────────────────────────────────┐   │
│   │ Young 영역 (새로 만든 객체)  │   │ Old 영역 (오래 살아남은 객체)     │   │
│   │  new Intro(), new ArrayList  │──▶│  스프링 빈, 캐시, 커넥션 풀...    │   │
│   └──────────────────────────────┘   └──────────────────────────────────┘   │
│                                                                             │
│  메타스페이스 — 클래스 정보 (힙 밖, 네이티브 메모리)                           │
│                                                                             │
│  ┌─ 스레드1 스택 ──────────┐   ┌─ 스레드2 스택 ──────────┐                   │
│  │ [main() 칸]             │   │ [run() 칸]              │  스레드마다 따로   │
│  │ [service.save() 칸]     │   │ [controller.list() 칸]  │  기본 약 1MB 안팎  │
│  │   지역변수 intro ──────────────▶ 힙의 Intro 객체를 가리킴(참조)            │
│  └─────────────────────────┘   └─────────────────────────┘                   │
└─────────────────────────────────────────────────────────────────────────────┘
```

| 영역 | 저장되는 것 | 크기 | 넘치면 |
|---|---|---|---|
| **스택** | 메서드 호출 1번 = 칸(프레임) 1개. 그 안에 **지역 변수, 파라미터**. 객체 자체가 아니라 **객체를 가리키는 주소(참조)** 만 들어감 | 작음 (스레드당 기본 약 1MB 안팎, `-Xss` 로 조절, OS마다 다름) | `StackOverflowError` |
| **힙** | `new` 로 만든 **모든 객체**와 배열 | 큼 (`-Xmx` 로 지정. 지정 안 하면 PC 메모리의 약 1/4) | `OutOfMemoryError: Java heap space` |

```java
public void save() {
    int count = 3;                     // 스택: 값 3 자체
    Intro intro = new Intro("홍길동");  // 스택: 주소(참조)만 / 힙: Intro 객체
}   // 메서드가 끝나면 스택 칸이 사라짐 → intro 참조도 사라짐 → 힙의 Intro는 "아무도 안 가리키는" 상태가 됨
```

## 2. `StackOverflowError` — 끝나지 않는 호출

### 🧪 직접 일으켜 보기

```powershell
cd 09_CS\샘플\cs-lab
java "-Dfile.encoding=UTF-8" MemoryLab.java stack
```
```
=== 1. 스택 넘치기 (끝나지 않는 재귀) ===
StackOverflowError! 약 22,832번 호출 후 스택이 가득 참
→ 원인 대부분: 종료 조건 없는 재귀, 또는 서로를 계속 부르는 메서드
```

> 호출 횟수는 PC·JVM 설정마다 다릅니다.

### 실무에서 만나는 곳

| 원인 | 예 | 해결 |
|---|---|---|
| **양방향 연관관계 + `toString`/JSON 변환** | `Intro` 가 `Member` 를, `Member` 가 다시 `Intro` 목록을 가짐 → Lombok `@ToString`·`@Data` 나 Jackson이 A→B→A→B... 무한 반복 | 엔티티를 그대로 응답하지 말고 **DTO로 변환**([SpringBoot 04 — A4](../Spring/SpringBoot/04_헷갈리기_쉬운_개념.md)), `@ToString.Exclude` |
| 종료 조건 없는 재귀 | 트리 메뉴를 재귀로 그리는데 부모-자식이 순환 참조된 데이터 | 종료 조건, 방문 체크 |
| 서로를 부르는 메서드 | `getA()` 가 `getB()` 를, `getB()` 가 `getA()` 를 호출 | 스택 트레이스에서 **반복되는 두 줄**을 찾기 |

> 💡 **스택 트레이스 읽는 법**: `StackOverflowError` 의 스택 트레이스는 같은 몇 줄이 **수천 번 반복**됩니다. 반복되는 묶음이 곧 범인입니다. 위 도입부 예시라면 `Intro.toString` ↔ `Member.toString` 입니다.

## 3. `OutOfMemoryError` — GC가 치울 수 없는 객체가 쌓임

### GC(가비지 컬렉터)는 무엇을 치우나

자바는 `free()` 같은 메모리 해제 코드를 쓰지 않습니다. **GC가 "더 이상 아무도 가리키지 않는 객체"를 찾아 자동으로 치웁니다.**

```
GC 루트 (스택의 지역 변수, static 필드 등)
   │
   ├──▶ 객체 A ──▶ 객체 B        ← 루트에서 닿음 = 살아 있음, 못 치움
   │
   └──▶ 객체 C

        객체 D ──▶ 객체 E        ← 루트에서 안 닿음 = 쓰레기, 치움
```

> 핵심: GC는 **"쓸모없는" 객체가 아니라 "닿을 수 없는" 객체**를 치웁니다. 다시는 안 쓸 객체라도 누군가(특히 `static` 컬렉션)가 붙잡고 있으면 **영원히 못 치웁니다.** 이것이 자바의 **메모리 누수**입니다.

### 🧪 직접 일으켜 보기 — 반드시 힙을 작게 제한하고

```powershell
java "-Xmx64m" "-Dfile.encoding=UTF-8" MemoryLab.java heap
```
```
=== 2. 힙 넘치기 (static 리스트에 계속 쌓기 = 메모리 누수) ===
최대 힙(-Xmx) = 64MB
  10MB 쌓음...
  20MB 쌓음...
  30MB 쌓음...
OutOfMemoryError: Java heap space  (약 30MB 에서 실패)
```

- 힙을 64MB로 줬는데 **30MB쯤에서 실패**합니다. 힙은 내 데이터만 쓰는 게 아니라 JVM 자신(이 실습에서는 소스를 컴파일하는 컴파일러까지)과 GC의 관리 방식도 공간을 차지하기 때문입니다. "설정한 최대치까지 다 쓸 수 있다"고 가정하면 안 됩니다.
- `-Xmx` 없이 실행하면 프로그램이 스스로 멈추고 안내합니다. 실습 PC는 최대 힙이 **8128MB**(PC 메모리의 약 1/4)로 잡혀 있었습니다. 이 상태로 돌리면 PC 전체가 느려질 수 있습니다.

### 실무 메모리 누수·OOM 단골

| 원인 | 예 | 해결 |
|---|---|---|
| **static 컬렉션에 넣기만** | `static Map<String, Object> cache` 에 요청마다 추가, 삭제 없음 | 크기 제한·만료가 있는 캐시 라이브러리(Caffeine 등), 또는 Redis |
| **한 번에 너무 많이 조회** | 100만 건을 `findAll()` 로 받아 `List` 에 담음, 엑셀 다운로드 | **페이징**, 스트리밍 조회, 배치 처리 |
| 큰 파일을 통째로 메모리에 | 업로드 파일을 `byte[]` 로 전부 읽기 | 스트림으로 조금씩 처리 |
| ThreadLocal 정리 안 함 | 스레드 풀의 스레드는 재사용되므로 값이 남음 | `finally` 에서 `remove()` |

## 4. GC의 동작 — 세대별 수집과 Stop-the-World

대부분의 객체는 **만들어지고 금방 버려집니다**(요청 하나 처리하는 동안 만든 DTO, 문자열 등). 그래서 JVM은 힙을 나눠 관리합니다.

| 영역 | 들어가는 것 | 수집 |
|---|---|---|
| **Young** | 새로 만든 객체 | 자주, 빠르게 (대부분 여기서 사라짐) |
| **Old** | 여러 번의 GC에서 살아남은 객체 (스프링 빈, 캐시) | 가끔, 오래 걸림 |

- **Stop-the-World**: GC가 일하는 동안 애플리케이션 스레드가 **잠깐 멈추는** 구간. 보통 아주 짧지만, Old 영역이 꽉 차서 큰 GC가 자주 돌면 응답이 **수백 ms~수 초씩 끊깁니다.**
- Java 9부터 기본 GC는 **G1**입니다. 대부분의 웹 서비스는 기본값으로 충분하고, GC 튜닝은 **측정한 뒤에** 합니다.

| 증상 | 의심할 것 |
|---|---|
| 응답이 주기적으로 뚝뚝 끊김 + CPU 높음 | GC가 너무 자주 돎. 힙이 거의 꽉 찬 상태 (누수의 전조) |
| 시간이 지날수록 메모리 사용량이 계속 오르고 안 내려감 | 메모리 누수 |
| 특정 기능(엑셀 다운로드 등) 실행 직후 OOM | 한 번에 너무 많이 조회 |

### 🔧 진단 도구 (알아만 두기)

```powershell
jcmd <PID> GC.heap_info                                   # 지금 힙 사용 현황
java -XX:+HeapDumpOnOutOfMemoryError -jar app.jar         # OOM 순간의 힙을 파일로 저장(덤프)
```
- 힙 덤프 파일을 분석 도구(Eclipse MAT, VisualVM 등)로 열면 **어떤 객체가 메모리를 가장 많이 잡고 있는지** 볼 수 있습니다.
- ⚠️ 힙 덤프에는 **메모리에 있던 개인정보·비밀번호·토큰이 그대로** 들어 있습니다. 운영 덤프는 보안 자료로 취급하고, 분석 후 삭제하세요.

> 🐳 **컨테이너에서 실행할 때**: 최신 JVM은 컨테이너의 메모리 제한을 인식해 힙 크기를 정합니다. 컨테이너 메모리를 512MB로 제한했다면 힙은 그 일부(기본 약 1/4)가 됩니다. 비율은 `-XX:MaxRAMPercentage=75.0` 처럼 조절합니다([06_Deploy](../06_Deploy/README.md)). 힙만 계산하고 스택·메타스페이스를 잊으면 **컨테이너가 OOM으로 강제 종료**될 수 있습니다.

## 5. `==` 와 `equals` — 메모리 그림으로 보기

```powershell
java "-Dfile.encoding=UTF-8" MemoryLab.java string
```
```
=== 3. 문자열 == vs equals ===
a == b          : true   (둘 다 풀의 같은 객체)
a == c          : false  (c 는 new 로 만든 다른 객체)
a.equals(c)     : true   (내용은 같음)
a == c.intern() : true   (intern 은 풀의 객체를 돌려줌)
실행 중 만든 "hello" == "hello" : false  ← 로그인 비교를 == 로 하면 이렇게 실패
s.concat("def") 후 s : abc   (String 은 불변 → 결과를 받아야 함: s = s.concat(...))
```

```
스택                       힙
 a ─────────┐
 b ─────────┼──▶ [ "hello" ]  ← 문자열 풀(String Pool): 리터럴은 같은 객체를 재사용
            │
 c ─────────────▶ [ "hello" ]  ← new String(): 내용은 같지만 다른 객체
 input ─────────▶ [ "hello" ]  ← 실행 중 만든 문자열(사용자 입력, DB 값)도 다른 객체
```

- **`==`** : 스택에 든 **주소**가 같은가 (같은 객체인가)
- **`equals`** : 힙에 있는 **내용**이 같은가
- 코드에 직접 쓴 `"hello"` 끼리는 풀 덕분에 `==` 가 **우연히 맞아서**, 테스트에선 통과하고 실제 입력값에서 실패합니다. 02 문서의 `Integer` 128 함정과 같은 구조입니다.

### `String` 은 불변(immutable)

`String` 은 한 번 만들면 내용이 안 바뀝니다. `concat`, `replace`, `toUpperCase` 는 **새 문자열을 돌려줄 뿐** 원본을 바꾸지 않습니다.

- 장점: 여러 스레드가 공유해도 안전(04 문서), 풀에서 재사용 가능, `HashMap` 키로 안전.
- 주의: 반복문에서 `s = s + "..."` 를 수만 번 하면 매번 새 객체가 생깁니다 → `StringBuilder` ([05_algorithm 01](../05_algorithm/01_기초_시간복잡도와_입출력.md)의 String 덧셈 함정).

## 6. 함정

| 오해 | 실제 |
|---|---|
| "자바는 GC가 있으니 메모리 누수가 없다" | GC는 **닿을 수 없는** 객체만 치움. static 컬렉션이 잡고 있으면 영원히 남음 |
| "OOM 나면 `-Xmx` 를 늘리면 된다" | 누수라면 시간만 늦출 뿐. 먼저 **무엇이 메모리를 잡고 있는지** 확인 |
| "`-Xmx64m` 이면 64MB까지 내 데이터를 넣을 수 있다" | JVM 자신과 GC 관리 공간도 힙을 씀 (실측 약 30MB에서 실패) |
| "StackOverflowError는 스택을 늘리면 해결" | 대부분 무한 재귀·순환 참조. `-Xss` 를 늘려도 무한은 못 채움 |
| "문자열은 `==` 로 비교해도 되더라" | 리터럴끼리만 우연히 맞음. 항상 `equals` |
| 운영 힙 덤프를 메신저로 공유 | 개인정보·토큰이 들어 있음. 보안 자료로 취급 |
