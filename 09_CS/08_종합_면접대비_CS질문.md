## 답변 공식 — 외운 정의보다 "내가 돌려 본 결과"

```

② 왜 / 차이       "count++ 가 읽기·계산·쓰기 3단계라서 중간에 다른 스레드가 끼어들 수 있기 때문입니다."

                   스프링 싱글톤 빈에 필드를 두면 같은 일이 생긴다는 걸 확인했습니다."
```

## A. 컴퓨터 구조 · 데이터 표현

<details>
<summary>Q1. 메모리 계층 구조를 설명하고, 웹 개발과 어떤 관련이 있는지 말해 주세요.</summary>

- CPU 레지스터·캐시 → RAM → SSD/HDD → 네트워크 순으로 **멀어질수록 느리고 크다**. 캐시와 RAM은 약 100배, RAM과 네트워크 왕복은 수천 배 이상 차이.
- 같은 원리로 웹에서도 **앱 메모리 캐시 ≪ DB ≪ 외부 API** 순으로 비싸다. 그래서 반복문 안의 DB 호출(N+1)을 줄이고, 자주 읽는 데이터는 캐시한다.
- 경험: "2차원 배열을 행 방향과 열 방향으로 순회하는 실험에서 같은 계산인데 약 28배 차이가 나는 걸 보고 캐시 지역성을 체감했습니다." (01)
</details>

<details>
<summary>Q2. 돈 계산에 double을 쓰면 안 되는 이유는?</summary>

- double은 2진수 부동소수점이라 0.1 같은 수를 정확히 표현하지 못한다. `0.1 + 0.2 = 0.30000000000000004`.
- 대안: 원 단위 정수(`long`), 소수점이 필요하면 `BigDecimal` — 단, **문자열 생성자**(`new BigDecimal("0.1")`)로 만들고, 나눗셈엔 반올림 규칙을 지정하고, 비교는 `compareTo`.
- 꼬리 질문 대비: "`new BigDecimal(0.1)` 은 왜 안 되나요?" → double의 오차가 그대로 들어가서 `0.1000000000000000055...` 가 된다. (02)
</details>

<details>
<summary>Q3. 문자 인코딩이 무엇이고, 한글이 깨지는 원인은?</summary>

- 유니코드는 글자에 번호를 붙인 표, UTF-8·MS949는 그 번호를 바이트로 저장하는 규칙. "가"는 UTF-8에서 3바이트, MS949에서 2바이트.
- 깨짐의 원인은 **저장할 때와 읽을 때의 인코딩이 다른 것** 하나. 영문은 두 방식이 같아서 한글만 깨진다.
- 실무: 소스·HTTP·DB(`utf8mb4`)·파일 입출력·외부 연계까지 전 구간을 맞춘다. 깨진 모양(`ì•ˆ`, `�`, `占쏙옙`)으로 원인을 추측할 수 있다. (02)
</details>

## B. 운영체제 · 동시성

<details>
<summary>Q4. 프로세스와 스레드의 차이는?</summary>

- 프로세스는 실행 중인 프로그램으로 **OS가 메모리를 따로 할당**한다. 스레드는 프로세스 안의 실행 흐름으로, 같은 프로세스의 **힙을 공유하고 스택은 각자** 가진다.
- 그래서 프로세스는 서로 격리돼 안전하지만 통신 비용이 크고, 스레드는 가볍고 협력이 쉽지만 **공유 데이터 문제(동시성 버그)** 가 생긴다.
- 실무 연결: 스프링 앱 하나가 프로세스 하나, 톰캣이 요청마다 스레드 풀(기본 최대 200개)의 스레드를 배정한다. (03)
</details>

<details>
<summary>Q5. 스프링 빈은 싱글톤인데, 동시에 여러 요청이 오면 문제가 없나요?</summary>

- 빈이 **무상태(stateless)** 면 문제없다. 요청 데이터는 파라미터와 지역 변수(스레드마다 따로 있는 스택)에만 두고, 필드에는 주입받은 `final` 협력 객체만 둔다.
- 필드에 요청별 값을 저장하면 요청 스레드들이 같은 필드를 덮어써 **다른 사용자의 데이터가 섞인다**.
- 경험: "스레드 10개로 20명의 요청을 동시에 처리하는 실험에서, 필드에 이름을 저장한 서비스는 20건 중 18건이 남의 이름을 응답했습니다. 그래서 서비스 클래스를 보면 final이 아닌 필드부터 확인합니다." (04)
</details>

<details>
<summary>Q6. 레이스 컨디션과 해결 방법을 설명해 주세요. volatile로 해결되나요?</summary>

- 정의와 원인: 답변 공식 예시 참고.
- 해결: `synchronized`(한 번에 한 스레드만), `AtomicInteger`(CAS로 잠금 없이 원자적 연산), `ConcurrentHashMap` 같은 스레드 안전 컬렉션.
- **volatile은 가시성만 보장**하고 원자성은 보장하지 않아 `count++` 문제를 해결하지 못한다. 실험에서도 volatile만 붙인 카운터는 40만 중 12만~25만만 남았다.
- 꼬리 질문 대비: "서버가 여러 대면?" → JVM 안의 잠금은 다른 서버를 모르므로 DB 수준(원자적 UPDATE, `SELECT ... FOR UPDATE`)에서 지켜야 한다. (04, 06)
</details>

<details>
<summary>Q7. 데드락이란? 어떻게 예방하나요?</summary>

- 두 개 이상의 스레드(트랜잭션)가 서로 상대가 가진 자원을 기다리며 영원히 진행하지 못하는 상태.
- 4가지 조건(상호 배제, 점유 대기, 비선점, 순환 대기)이 모두 성립할 때 생기므로 하나를 깨면 된다. 가장 실용적인 건 **잠금 순서 통일**(예: 계좌번호가 작은 쪽부터)과 **타임아웃**.
- 운영에서 서버가 멈추면 재시작 전에 `jstack` 으로 스레드 덤프를 떠서 `Found one Java-level deadlock` 을 확인한다. (04)
</details>

## C. JVM

<details>
<summary>Q8. JVM의 스택과 힙 영역의 차이는?</summary>

- 스택: 스레드마다 따로, 메서드 호출마다 프레임이 쌓이고 지역 변수·참조가 저장. 메서드가 끝나면 사라짐. 넘치면 `StackOverflowError`.
- 힙: 모든 스레드가 공유, `new` 로 만든 객체 저장, GC가 관리. 넘치면 `OutOfMemoryError`.
- 실무: `StackOverflowError` 는 대부분 무한 재귀나 **엔티티 양방향 연관관계의 toString/JSON 순환**. OOM은 static 컬렉션 누수나 대량 조회. (05)
</details>

<details>
<summary>Q9. GC는 어떻게 동작하나요? 자바에도 메모리 누수가 있나요?</summary>

- GC 루트(스택의 지역 변수, static 필드 등)에서 **닿을 수 없는** 객체를 찾아 회수한다. 대부분의 객체가 금방 버려진다는 점을 이용해 Young/Old 영역으로 나눠 관리한다. Java 9부터 기본은 G1.
- 누수 있다. GC는 "쓸모없는" 객체가 아니라 "닿을 수 없는" 객체만 치우므로, static Map 캐시처럼 계속 참조를 쥐고 있으면 회수되지 않는다.
- 경험: "힙을 64MB로 제한하고 static 리스트에 계속 넣는 실험으로 OOM을 재현했는데, 설정값의 절반 정도에서 실패하는 걸 보고 힙을 JVM도 같이 쓴다는 걸 알았습니다." (05)
</details>

<details>
<summary>Q10. ==와 equals의 차이는?</summary>

- `==` 는 참조(주소) 비교, `equals` 는 내용 비교(클래스가 재정의한 기준).
- 문자열 리터럴은 String Pool에서 재사용돼 `==` 가 우연히 true가 되고, `Integer` 는 -128~127이 캐시돼 같은 함정이 있다. 그래서 테스트에선 통과하고 운영 데이터에서 실패한다.
- `equals` 를 재정의하면 `hashCode` 도 함께 재정의해야 `HashMap`·`HashSet` 에서 올바르게 동작한다. (02, 05)
</details>

## D. 데이터베이스

<details>
<summary>Q11. 트랜잭션의 ACID와 격리 수준을 설명해 주세요.</summary>

- ACID: 원자성(전부 or 전무), 일관성(규칙 유지), 격리성(동시 트랜잭션 간 간섭 제어), 지속성(커밋은 영구).
- 격리 수준: READ UNCOMMITTED < READ COMMITTED < REPEATABLE READ < SERIALIZABLE. 높을수록 Dirty Read, Non-Repeatable Read, Phantom Read를 더 막지만 동시 처리 성능이 떨어진다.
- 기본값: MySQL InnoDB는 REPEATABLE READ, Oracle·PostgreSQL은 READ COMMITTED. 로컬 H2(READ COMMITTED)와 운영 MySQL이 다를 수 있다. (06)
</details>

<details>
<summary>Q12. 트랜잭션을 썼는데도 동시 수정 문제가 생길 수 있나요?</summary>

- 있다. **갱신 분실**: 두 트랜잭션이 같은 값을 읽고 각자 계산해 덮어쓰면 먼저 쓴 쪽이 사라진다. 기본 격리 수준에서는 막아 주지 않는다.
- 해결: ① `UPDATE ... SET balance = balance - ?` 처럼 계산을 한 문장으로, ② `SELECT ... FOR UPDATE` 비관적 락, ③ `@Version` 낙관적 락.
- 경험: "잔액 1만 원에서 3천 원, 5천 원 동시 출금을 재현했더니 최종 잔액이 5천 원으로 3천 원이 사라졌고, 원자적 UPDATE와 FOR UPDATE로 바꾸니 2천 원이 됐습니다." (06)
</details>

<details>
<summary>Q13. 인덱스란? 언제 쓰고, 언제 안 쓰이나요?</summary>

- 컬럼 값을 정렬해 둔 별도 자료구조(주로 B-Tree)로, 전체 스캔 없이 O(log N)에 가깝게 찾는다. 대신 쓰기 성능과 저장 공간을 희생한다.
- WHERE·JOIN·ORDER BY에 자주 쓰이고 값이 다양한 컬럼에 만든다.
- 안 쓰이는 경우: `LIKE '%값'`, 컬럼에 함수 적용(`LOWER(email)`), 타입 불일치, 복합 인덱스 앞 컬럼 생략.
- 경험: "30만 건에서 인덱스를 만들기 전후로 실행 계획을 봤더니 tableScan이 인덱스 검색으로 바뀌고 약 150배 빨라졌습니다. 반대로 LOWER(email)로 조회하면 인덱스가 있어도 다시 tableScan이 됐습니다." (06)
</details>

## E. 객체지향 · 설계

<details>
<summary>Q14. 객체지향의 특징과 SOLID를 설명해 주세요.</summary>

- 캡슐화, 추상화, 상속, 다형성. 각각 한 줄 정의 + 예(07 문서 1절 표).
- SOLID는 다 외우기보다 **스프링 예로 두세 개를 확실히**: SRP → Controller/Service/Repository 분리, DIP → Service가 Repository 인터페이스에 의존하고 스프링이 구현체를 주입, OCP → 결제 수단 추가 시 구현체만 추가.
- 균형: "원칙을 과하게 적용하면 오히려 복잡해지므로, 변경 가능성이 실제로 있는 곳에 적용합니다." (07)
</details>

<details>
<summary>Q15. @Transactional은 어떻게 동작하고, 동작하지 않는 경우는?</summary>

- 스프링이 빈 앞에 **프록시**를 만들어, 메서드 호출 전에 트랜잭션을 시작하고 끝나면 커밋, 런타임 예외면 롤백한다.
- 같은 클래스 안에서 `this.method()` 로 호출하면 프록시를 거치지 않아 적용되지 않는다. `private` 메서드도 마찬가지. 기본 설정에선 체크 예외로는 롤백되지 않는다.
- 그리고 `@Transactional` 이 동시 수정 문제(갱신 분실)를 막아 주지는 않는다. (06, 07)
</details>

| "서버가 응답이 없는데 CPU는 0%예요" | 데드락, 스레드 풀 고갈(느린 외부 호출) | 재시작 전에 `jstack` 스레드 덤프 |
| "며칠 지나면 서버가 OOM으로 죽어요" | 메모리 누수 (static 캐시 등) | 힙 덤프 분석 (보안 자료 취급) |
| "검색이 너무 느려요" | 인덱스 미사용 (`LIKE '%...'`, 함수) | `EXPLAIN` 의 `type: ALL` |
| "엑셀로 받은 파일 한글이 깨져요" | 인코딩 불일치 (UTF-8 vs MS949) | 파일을 16진수로 열어 바이트 확인, 연계 명세 확인 |
| "정산 금액이 몇 원씩 안 맞아요" | double 사용 | 금액 타입을 `long`·`BigDecimal` 로 |
