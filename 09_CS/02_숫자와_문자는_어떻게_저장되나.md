# 02. 숫자와 문자는 어떻게 저장되나

> 🎯 목표: **정수 오버플로, 실수 오차, Integer 비교, 한글 깨짐**이 왜 생기는지 설명하고, 깨진 글자의 **모양만 보고** 원인을 추측할 수 있다.

---

## 도입 — 에러 없이 틀리는 코드

아래 코드는 모두 **컴파일도 되고, 예외도 안 납니다.** 그런데 결과가 틀립니다.

```java
int millis = 30 * 24 * 60 * 60 * 1000;     // 30일을 밀리초로     → -1702967296
double total = 0.1 + 0.2;                   // 0.3 원             → 0.30000000000000004
Integer a = 128, b = 128;  a == b;          // 같은 값인데        → false
new String(bytes, "MS949");                 // 한글 읽기          → 占쏙옙
```

가장 위험한 버그는 **에러가 나지 않는 버그**입니다. 테스트를 대충 하면 운영까지 갑니다.
이 문서는 컴퓨터가 숫자와 글자를 **비트로 어떻게 저장하는지** 보고, 이 네 가지가 왜 생기는지 풉니다.

### 🧪 먼저 실행해 보기

```powershell
cd 09_CS\샘플\cs-lab
java "-Dfile.encoding=UTF-8" NumberLab.java
java "-Dfile.encoding=UTF-8" EncodingLab.java
```

## 1. 정수 — 칸 수가 정해진 계량기

`int` 는 **32비트**(4바이트)라는 정해진 칸에 숫자를 담습니다. 자동차 주행거리계가 999999 다음에 000000으로 돌아가듯, 칸이 넘치면 **뒤집힙니다**.

```
Integer.MAX_VALUE      = 2147483647
Integer.MAX_VALUE + 1  = -2147483648   <- 에러 없이 음수가 됨
2진수 MAX_VALUE        = 1111111111111111111111111111111   (31자리, 맨 앞 부호비트 0 생략)
2진수 MAX_VALUE + 1    = 10000000000000000000000000000000  (부호비트가 1 → 음수)
-1 의 2진수            = 11111111111111111111111111111111  (2의 보수: 모든 비트가 1)
```

- 맨 앞 비트는 **부호**입니다(0이면 양수, 1이면 음수). 음수는 **2의 보수**라는 방식으로 저장합니다. 덧셈 회로 하나로 뺄셈까지 처리하려고 고안한 방식이라, 세부 계산법보다 "**최댓값에 1을 더하면 최솟값이 된다**"는 결과를 기억하세요.
- `int` 범위는 약 **±21억**입니다. 커 보이지만 실무에선 금방 넘습니다.

### 실무에서 넘치는 곳

```
30일을 밀리초로 (int)  = -1702967296   <- 틀림
30일을 밀리초로 (long) = 2592000000
Math.multiplyExact     → ArithmeticException: integer overflow
```

| 상황 | 해결 |
|---|---|
| 시간 계산 (밀리초, 나노초) | `long` 사용. `24L` 처럼 **한 숫자만 L을 붙여도** 계산 전체가 long으로 됨 |
| 누적 조회수, 금액 합계, 파일 크기 | `long` 사용. DB 컬럼도 `BIGINT` |
| 넘치면 안 되는 계산 | `Math.addExact`, `Math.multiplyExact` → 넘치면 **예외**를 던져 조용히 틀리지 않음 |

> 💡 엔티티의 ID를 `Long` 으로 쓰는 것도 같은 이유입니다. 데이터가 21억 건을 넘을 일은 드물지만, 바꾸려면 DB 마이그레이션이 필요해 처음부터 넉넉하게 잡습니다.

## 2. 실수 — 2진수로는 0.1을 정확히 못 적는다

10진수로 1/3 = 0.3333... 을 끝까지 못 적듯, **2진수로는 0.1을 끝까지 못 적습니다.** `double` 은 64비트 안에서 잘라 근삿값을 저장합니다.

```
0.1 + 0.2              = 0.30000000000000004
0.1 + 0.2 == 0.3 ?     = false
0.1 을 10번 더하면     = 0.9999999999999999
1.1 * 3                = 3.3000000000000003
```

### 돈 계산에 `double` 을 쓰면 안 되는 이유

몇 원짜리 오차가 수백만 건 쌓이면 정산이 맞지 않습니다. 돈은 둘 중 하나로 다룹니다.

| 방법 | 언제 | 예 |
|---|---|---|
| **`long` 으로 최소 단위 저장** | 원화처럼 소수점이 없는 경우 | 10,000원 → `10000L` |
| **`BigDecimal`** | 이자율, 환율, 소수점 이하 계산 | DB 컬럼은 `DECIMAL(15,2)` 같은 고정소수점 |

### `BigDecimal` 의 함정 3가지

```
new BigDecimal(0.1)    = 0.1000000000000000055511151231257827021181583404541015625   <- double 오차가 그대로
new BigDecimal("0.1")  = 0.1
BigDecimal.valueOf(0.1)= 0.1
1 / 3 (규칙 없음)      → ArithmeticException: Non-terminating decimal expansion; ...
1 / 3 (소수 2자리 반올림)= 0.33
1.0 equals 1.00 ?      = false   <- 자릿수가 달라서 false
1.0 compareTo 1.00     = 0      <- 0 이면 값이 같음
```

1. **문자열로 만들기**: `new BigDecimal(0.1)` 은 이미 오차가 낀 double을 정밀하게 옮길 뿐입니다. `new BigDecimal("0.1")` 또는 `BigDecimal.valueOf(0.1)`.
2. **나누기에는 반올림 규칙 필수**: `divide(값, 자릿수, RoundingMode.HALF_UP)`. 규칙을 정하는 건 개발자가 아니라 **업무 규정**(절사인지 반올림인지)이므로 기획에 확인하세요.
3. **값 비교는 `compareTo`**: `equals` 는 소수점 자릿수(scale)까지 비교합니다.

> ⚠️ **프론트엔드도 같은 문제**: 자바스크립트의 숫자는 전부 `double` 입니다. 그래서 `9007199254740993` 같은 **2⁵³을 넘는 정수는 JS에서 정확히 표현되지 않습니다.** 자바의 `Long` ID가 아주 큰 값이면 JSON으로 React에 보낼 때 끝자리가 바뀔 수 있어, 이런 ID는 문자열로 보내기도 합니다([Front-Back](../Spring/Front-Back/README.md)).

## 3. `Integer` 를 `==` 로 비교하면 안 되는 이유

```
Integer 127 == 127     = true    <- -128~127 은 같은 객체를 재사용(캐시)
Integer 128 == 128     = false   <- 서로 다른 객체 → 주소 비교라 false
Integer 128 equals 128 = true    <- 값 비교는 equals
```

- `int` 는 **값**, `Integer` 는 **객체**입니다. 객체에 `==` 를 쓰면 "같은 객체인가(주소)"를 비교합니다.
- 자바는 자주 쓰는 **-128~127** 의 `Integer` 객체를 미리 만들어 재사용합니다(캐시). 그래서 작은 숫자로 테스트하면 `==` 가 우연히 맞고, **운영 데이터(128 이상)에서만 틀립니다.**
- 엔티티 ID는 보통 `Long` 이라서 `if (post.getWriterId() == loginId)` 같은 코드가 이 버그의 단골입니다. → `Objects.equals(a, b)` 또는 `a.equals(b)`.

> 같은 이유로 `String` 도 `==` 로 비교하면 안 됩니다. 05 문서에서 메모리 그림으로 다시 봅니다.

## 4. 문자 — 글자는 "번호표"다

컴퓨터는 글자를 모릅니다. **글자마다 번호를 정해 둔 약속표**에 따라 숫자로 저장합니다.

| 용어 | 뜻 |
|---|---|
| **문자 집합 (Unicode)** | 전 세계 글자에 번호를 붙인 표. "가" = U+AC00, "A" = U+0041, "😀" = U+1F600 |
| **인코딩 (UTF-8, MS949...)** | 그 번호를 **몇 바이트로, 어떤 비트로** 저장할지 정한 규칙 |
| **인코딩 / 디코딩** | 글자 → 바이트로 바꾸기 / 바이트 → 글자로 바꾸기 |

### 같은 글자, 다른 바이트

```
A     length()=1  UTF-8 1바이트 [41]                  MS949 1바이트 [41]
가    length()=1  UTF-8 3바이트 [EA B0 80]            MS949 2바이트 [B0 A1]
한글  length()=2  UTF-8 6바이트 [ED 95 9C EA B8 80]   MS949 4바이트 [C7 D1 B1 DB]
😀    length()=2  UTF-8 4바이트 [F0 9F 98 80]         MS949 1바이트 [3F]
```

여기서 읽어 낼 수 있는 것:

1. **영문은 둘 다 똑같다** (ASCII 호환) → 그래서 **영문은 멀쩡하고 한글만 깨집니다.**
2. **한글은 UTF-8에서 3바이트, MS949에서 2바이트** → 같은 바이트를 다른 규칙으로 읽으면 엉뚱한 글자가 됩니다.
3. **이모지는 MS949에 없다** → `?`(3F)로 바뀌어 **데이터가 영영 사라집니다.**
4. **`length()` 는 바이트 수도, 눈에 보이는 글자 수도 아니다** → 자바 `char` 개수입니다. 이모지는 2로 나옵니다. 정확한 글자 수는 `codePointCount`, 바이트 수는 `getBytes(UTF_8).length`.

| 인코딩 | 어디서 쓰나 |
|---|---|
| **UTF-8** | 웹 표준. HTML, JSON, 리눅스, MySQL 8.0 기본값, Java 18 이상의 기본값 |
| **MS949 (CP949)** | 한글 Windows의 기본값. EUC-KR을 확장한 것. 오래된 공공·금융 시스템, 엑셀 CSV |

## 5. 한글 깨짐 — 깨진 모양으로 원인을 추측하라

깨짐의 원인은 **딱 하나**입니다. **저장(인코딩)할 때의 규칙 ≠ 읽을(디코딩) 때의 규칙.**

```
원본                           : 안녕하세요
UTF-8로 저장 → MS949로 읽기    : �븞�뀞�븯�꽭�슂
UTF-8로 저장 → 서유럽(1252)로 읽기: ì•ˆë…•í•˜ì„¸ìš”
MS949로 저장 → UTF-8로 읽기    : �ȳ��ϼ���
```

### 깨짐 모양 진단표

| 보이는 모양 | 무슨 일이 있었나 | 흔한 장소 |
|---|---|---|
| `ì•ˆë…•`, `Ã¬...` (라틴 문자 + 기호) | **UTF-8** 바이트를 **서유럽 문자(ISO-8859-1/1252)** 로 읽음 | 옛날 톰캣 설정, 인코딩 지정 없는 HTTP 처리 |
| `�` (물음표 다이아몬드) 섞임 | **UTF-8로 읽을 수 없는 바이트** (대개 MS949로 저장된 것을 UTF-8로 읽음) | Windows에서 만든 CSV·텍스트를 서버에서 읽을 때 |
| `占쏙옙`, `占싹쇽옙` | `�` 가 **저장된 뒤** 다시 MS949로 읽힘. **이미 원본이 사라진 상태** | 오래된 게시판, 로그 파일 |
| `???` (진짜 물음표) | 대상 인코딩에 그 글자가 **없어서** `?` 로 바뀌어 저장됨 | 이모지를 MS949·MySQL `utf8`(utf8mb3)에 저장 |
| 한글은 다 깨지고 영문·숫자는 멀쩡 | 위 모든 경우의 공통점 (ASCII 호환) | |

### 깨진 걸 되돌릴 수 있을까?

```
ISO-8859-1 로 잘못 읽은 것 복구 : 안녕하세요         <- 1바이트=1글자라 바이트가 보존돼 복구됨
UTF-8 로 잘못 읽은 것 복구      : 占싫놂옙占싹쇽옙占쏙옙   <- '�'로 바뀐 순간 원래 바이트가 사라져 복구 불가
```

- 화면에서만 잘못 **읽은** 것이면 바이트가 살아 있어 복구될 수 있습니다.
- `�` 나 `?` 로 바뀐 채 **DB에 저장**됐다면 복구할 수 없습니다. **그래서 깨짐은 저장 전에 막아야 합니다.**

### 🧪 일부러 깨뜨려 보기

`-Dfile.encoding=UTF-8` 을 **빼고** 실행해 보세요.

```powershell
java EncodingLab.java
```
```
=== 0. �?�? ?�� JVM?�� 기본 ?��코딩 ===
Charset.defaultCharset() = x-windows-949
```

- Java 17은 기본 인코딩을 **OS 설정**에서 가져옵니다. 한글 Windows는 MS949(`x-windows-949`)입니다.
- 소스 파일은 UTF-8로 저장돼 있는데, 자바가 MS949로 읽어서 **소스 속 한글 문자열 자체가 깨졌습니다.**
- Java 18부터는 OS와 상관없이 기본값이 UTF-8로 바뀌었습니다(JEP 400). **"내 PC(Java 17, Windows)에서는 깨지는데 서버(리눅스)에서는 멀쩡"** 같은 차이가 이렇게 생깁니다.

## 6. 실무 연결 — 인코딩을 맞춰야 하는 다섯 군데

데이터가 지나가는 모든 구간에서 규칙이 같아야 합니다. 하나라도 다르면 깨집니다.

| 구간 | 확인할 것 |
|---|---|
| ① 소스 파일 | IDE 파일 인코딩 UTF-8, Gradle `options.encoding = 'UTF-8'` |
| ② HTTP 요청·응답 | 스프링부트는 기본 UTF-8 (Boot 4.1 기준 `spring.servlet.encoding.charset` 기본값 UTF-8). 응답 헤더 `Content-Type: ...; charset=UTF-8` 확인 |
| ③ DB | MySQL은 **`utf8mb4`** 를 쓸 것. MySQL의 `utf8` 은 실제로는 3바이트까지만 저장하는 `utf8mb3` 라서 **이모지가 들어가지 않습니다** |
| ④ 파일 입출력 | `Files.readString(path, StandardCharsets.UTF_8)` 처럼 **인코딩을 항상 명시**. 기본값에 기대지 않기 |
| ⑤ 외부 연계·엑셀 | 공공기관 연계 파일이나 엑셀용 CSV는 **MS949를 요구**하는 경우가 아직 있음 → 연계 명세서에서 인코딩부터 확인 |

> 💡 **BOM 주의**: 메모장 등이 UTF-8 파일 맨 앞에 붙이는 `EF BB BF` 3바이트입니다. 눈에 안 보이지만 문자열 비교를 깨뜨립니다.
> ```
> BOM + "GET" 을 문자열로 읽으면 화면엔 [﻿GET] 처럼 보이지만
> length() = 4,  equals("GET") = false,  첫 글자 코드 = U+FEFF
> ```
> [07_Network](../07_Network/샘플/socket-lab/README.md)에서 PowerShell 파이프로 보낸 HTTP 요청이 400이 났던 원인입니다. CSV 첫 컬럼 이름이 이상하게 매칭이 안 될 때도 의심하세요.

스프링부트 앱에서 한글이 깨질 때의 체크리스트는 [SpringBoot 04 — B4. 한글이 깨져요](../Spring/SpringBoot/04_헷갈리기_쉬운_개념.md)에도 있습니다.

## 7. 함정

| 오해 | 실제 |
|---|---|
| "int로 충분하다" | 시간(ms)·합계·누적값은 금방 21억을 넘음. 넘쳐도 **에러가 안 남** |
| "double은 정밀하니까 돈 계산해도 된다" | 0.1도 정확히 못 적음. `long`(원 단위) 또는 `BigDecimal("문자열")` |
| "`Integer`도 숫자니까 `==` 로 비교" | 127까지만 우연히 맞음. `equals` |
| "`length()` 로 DB 컬럼 길이 검사" | `length()` 는 char 개수. 바이트 기준 컬럼이면 `getBytes(UTF_8).length`. MySQL `VARCHAR(n)` 은 문자 수 기준이지만 DB마다 다르니 확인 |
| "MySQL 문자셋은 utf8이면 된다" | `utf8mb4` 여야 이모지 저장 가능 |
| "한글 깨짐은 화면 문제다" | 저장 단계에서 깨지면 **데이터가 영구 손실**. 입력→저장→조회 중 어디서 깨지는지 구간을 나눠 확인 |
