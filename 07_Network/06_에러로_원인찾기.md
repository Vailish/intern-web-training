# 06. 에러로 원인 찾기 ⭐ 실무

> 🎯 목표: 접속 에러를 보면 **"어느 단계(DNS → TCP → TLS → HTTP → 앱)에서 실패했는지"** 를 바로 짚고, 다음에 무엇을 확인할지 정할 수 있다.

---

## 도입

"DB 연결이 안 돼요", "API 호출이 안 돼요" 라고만 말하면 아무도 도와줄 수 없습니다.
**"DNS는 되는데 TCP 연결에서 timeout이 납니다"** 라고 말할 수 있으면, 원인 후보가 순식간에 줄어듭니다.

---

## 1. 진단은 아래 단계부터 순서대로

```
 ① DNS      이름 → IP 변환이 되나?           실패: UnknownHostException, curl exit 6
     │ OK
 ② TCP      그 IP:포트에 연결이 되나?
     │        ├ 응답이 RST (거부)             실패: Connection refused, curl exit 7
     │        └ 응답이 아예 없음              실패: Connect timed out, curl exit 28
     │ OK
 ③ TLS      (HTTPS만) 암호화 협상이 되나?    실패: SSLHandshakeException, curl exit 35 / 60
     │ OK
 ④ HTTP     요청 형식·경로가 맞나?            4xx  (400, 401, 403, 404, 405 ...)
     │ OK
 ⑤ 앱       서버 코드가 정상 처리했나?        5xx  (500 ...)
```

**아래 단계가 실패하면 위 단계는 시작도 못 합니다.** 그러니 아래부터 확인합니다.
반대로 **HTTP 상태 코드(4xx, 5xx)를 받았다면 ①~③은 이미 성공한 것**입니다. 네트워크는 정상이고 요청이나 앱을 봐야 합니다.

## 2. 에러 → 원인 대응표

| 에러 (자바) | curl | 실패 단계 | 의미 | 먼저 확인할 것 |
|---|---|---|---|---|
| `UnknownHostException` | exit **6** | ① DNS | 이름을 IP로 못 바꿈 | 호스트명 **오타**, DNS 설정, 사내망 전용 이름인지, Docker 네트워크 |
| `ConnectException: Connection refused` | exit **7** | ② TCP | 상대 컴퓨터는 응답(**RST**)했지만 **그 포트에 아무도 없음** | 서버 프로세스가 **떠 있나**, **포트 번호**가 맞나, 바인딩 주소(`127.0.0.1` 만?) |
| `SocketTimeoutException: Connect timed out` | exit **28** | ② TCP | SYN을 보냈는데 **응답이 아예 없음** | **방화벽·보안그룹**이 막고 있나, **IP**가 맞나, 서버가 꺼져 있나 |
| `SocketTimeoutException: Read timed out` | exit 28 | ④⑤ | 연결은 됐는데 **응답이 너무 늦음** | 서버 처리 지연(느린 SQL 등), 타임아웃 설정 |
| `SSLHandshakeException` | exit **35** / **60** | ③ TLS | 인증서·암호 방식 문제 | 인증서 만료, 사설 인증서, 프로토콜 버전 |
| HTTP **4xx** | 성공(0) + 상태코드 | ④ HTTP | **요청**이 잘못됨 | URL 경로, 메서드, 헤더, 인증 |
| HTTP **5xx** | 성공(0) + 상태코드 | ⑤ 앱 | **서버 코드**에서 예외 | **서버 로그**의 스택트레이스 |

> ⭐ **refused vs timeout — 가장 중요한 구분**
> - **refused**: "문을 두드렸더니 **'없어요'** 라고 대답함" → 집(서버 컴퓨터)은 있음. **프로그램·포트 문제**
> - **timeout**: "문을 두드렸는데 **아무 대답이 없음**" → 중간에서 막혔거나 집이 없음. **방화벽·네트워크 문제**
>
> (예외: 일부 방화벽은 일부러 RST를 보내 거부하기도 합니다. 그래도 첫 판단은 위 기준으로 충분합니다.)

## 3. 실습 — 모든 에러를 직접 만들어 보기

socket-lab의 `TcpClient` 는 연결에 실패하면 **실패 단계와 의미를 알려 주도록** 만들었습니다.

```powershell
cd 07_Network\샘플\socket-lab
```

### ① DNS 실패
```powershell
java "-Dfile.encoding=UTF-8" TcpClient.java no-such-host.invalid 80
```
```
[실패 단계] DNS
[의미]      이름을 IP로 바꾸지 못했습니다. 호스트 이름 오타나 네트워크 연결을 확인하세요.
[원본 예외] java.net.UnknownHostException: no-such-host.invalid
```
> `.invalid` 는 국제 표준으로 **절대 존재하지 않도록 예약된** 최상위 도메인이라 실습용으로 안전합니다.

### ② TCP 거부 (refused)
```powershell
java "-Dfile.encoding=UTF-8" TcpClient.java localhost 9999
```
```
[실패 단계] TCP
[의미]      상대 컴퓨터에는 닿았지만, 그 포트에서 기다리는 프로그램이 없습니다(RST 수신). ...
[원본 예외] java.net.ConnectException: Connection refused: no further information
```
**즉시** 실패합니다. Wireshark에서 SYN → RST를 볼 수 있습니다([04 문서](./04_TCP_UDP_3way_handshake.md) 실습 C).

### ③ TCP 타임아웃 (timeout)
```powershell
java "-Dfile.encoding=UTF-8" TcpClient.java 10.255.255.1 9000
```
```
[실패 단계] TCP
[의미]      3000ms 동안 아무 응답이 없습니다(SYN에 무응답). 방화벽·보안그룹 차단이나 잘못된 IP를 의심하세요.
[원본 예외] java.net.SocketTimeoutException: Connect timed out
```
**3초를 기다린 뒤** 실패합니다(`TcpClient` 의 타임아웃이 3초). `10.255.255.1` 은 보통 아무도 쓰지 않는 사설 IP라, SYN을 보내도 대답이 없습니다.
> 사내 네트워크 구성에 따라 다른 결과가 나올 수도 있습니다. 그때는 강사에게 다른 IP를 받으세요.

### ④⑤ HTTP 단계 (스프링 intro 앱을 켠 상태에서)
```powershell
curl.exe -s -o NUL -w "%{http_code}`n" http://localhost:8080/nope        # 404 ← 요청 문제
curl.exe -s -o NUL -w "%{http_code}`n" http://localhost:8080/intro/999   # 500 ← 앱 문제
```
`/intro/999` 의 500은 intro 앱의 `IntroService.findById()` 가 "존재하지 않는 자기소개서" 예외를 던지는데, 처리하는 코드가 없어서 생깁니다. **앱 콘솔에 스택트레이스가 찍혀 있을 것**입니다. 네트워크는 아무 잘못이 없습니다.

### curl로 같은 실험 (종료 코드 확인)
```powershell
curl.exe -s -o NUL http://no-such-host.invalid/;                  "exit=$LASTEXITCODE"   # 6
curl.exe -s -o NUL http://localhost:9999/;                        "exit=$LASTEXITCODE"   # 7
curl.exe -s -o NUL --connect-timeout 3 http://10.255.255.1:8080/; "exit=$LASTEXITCODE"   # 28
```

## 4. 도구별 사용법

| 도구 | 확인하는 단계 | 명령 |
|---|---|---|
| `nslookup` | ① DNS | `nslookup db.example.com` |
| `Test-NetConnection` | ① + ② | `Test-NetConnection 서버 -Port 3306` |
| `curl.exe -v` | ①~④ 한 번에 | `curl.exe -v http://서버:8080/` |
| `netstat -ano` | 서버 쪽 LISTEN 확인 | `netstat -ano \| findstr :8080` |
| Wireshark | 패킷 수준 증거 | SYN에 RST가 오나, 아무것도 안 오나 |
| `tracert` | 경로 중 어디까지 가나 | `tracert -d 8.8.8.8` |

### Test-NetConnection 결과 읽기 (실측)

| 상황 | 출력 | 걸린 시간 |
|---|---|---|
| 성공 | `TcpTestSucceeded : True` | 즉시 |
| DNS 실패 | 경고 `Name resolution of no-such-host.invalid failed` | 즉시 |
| refused | 경고 `TCP connect to (::1 : 9999) failed`, `TcpTestSucceeded : False` | **즉시** |
| timeout | 경고 `TCP connect to (10.255.255.1 : 8080) failed` + `Ping ... TimedOut` | **수십 초** (실측 36초) |

> ⚠️ `Test-NetConnection` 은 refused와 timeout을 **같은 문구**로 보여 줍니다. **걸린 시간**으로 구분하세요(즉시 실패 = refused, 한참 기다림 = timeout). 정확히 보려면 `TcpClient` 나 Wireshark를 쓰세요.

### tracert 결과에 `*` 가 있어도 놀라지 말 것
```
  1    <1 ms    <1 ms    <1 ms  192.168.0.1          ← 공유기(기본 게이트웨이)
  2     *        *        *     Request timed out.
  3     1 ms     1 ms     1 ms  10.0.0.29            ← 그다음 라우터
```
(실측 결과의 형태를 유지하되 IP는 예시로 바꿨습니다. 사내 네트워크 경로는 외부에 공유하지 않는 정보입니다.)
2번 줄이 `*` 인데 3번은 응답이 왔습니다. 중간 장비가 **tracert(ICMP) 응답만 안 하도록** 설정된 것이지 고장이 아닙니다. 마찬가지로 **`ping` 이 안 된다고 서버가 죽은 건 아닙니다.** 많은 서버가 ping을 막아 둡니다. 서비스 확인은 **실제 포트로** (`Test-NetConnection -Port`) 하세요.

## 5. 스프링·DB 에러 메시지 읽는 법

실무 에러는 여러 겹으로 포장되어 나옵니다. **맨 아래 `Caused by`** 가 진짜 원인입니다.

예시 구조 (바깥쪽 예외 이름은 상황마다 다릅니다. 06_Deploy에서는 `org.hibernate.exception.JDBCConnectionException: unable to obtain isolated JDBC connection` 이었습니다):

```
(바깥쪽: 스프링·Hibernate가 감싼 예외)
  ...
Caused by: com.mysql.cj.jdbc.exceptions.CommunicationsException: Communications link failure
  ...
Caused by: java.net.UnknownHostException: intro-db          ← 진짜 원인: DNS 단계
       또는 java.net.ConnectException: Connection refused   ← 진짜 원인: TCP 거부
       또는 java.net.SocketTimeoutException: ...            ← 진짜 원인: TCP 무응답
```

- MySQL 드라이버의 **`Communications link failure`** 는 "연결 실패"라는 **포장지**일 뿐입니다. 06_Deploy에서 본 이 에러의 진짜 원인은 그 아래 `Caused by` 에 있습니다.
- 스프링 `RestClient` 로 외부 API를 부를 때도 `ResourceAccessException: I/O error on GET request for "...": Connection refused` 처럼 **메시지 끝에 진짜 원인**이 붙습니다.

## 6. 상황별 연습 문제

<details>
<summary><b>Q1.</b> 로컬에서 잘 되던 앱을 개발 서버에 올렸더니 <code>Connect timed out</code> 으로 DB 접속이 안 된다. DB 서버는 켜져 있다고 한다.</summary>

**② TCP 단계, 무응답** → 방화벽 의심. 앱 서버 → DB 서버 3306/TCP 가 방화벽(또는 AWS 보안그룹)에서 허용되어 있는지 확인. 공공·SI 현장이라면 방화벽 오픈 신청이 되어 있는지 확인.
</details>

<details>
<summary><b>Q2.</b> <code>Connection refused</code> 가 난다. 서버 담당자는 MySQL이 "분명히 떠 있다"고 한다.</summary>

**② TCP 단계, 거부** → 컴퓨터는 응답했으니 방화벽보다는 **포트·바인딩** 문제. ① 포트 번호(3306 vs 3307), ② MySQL이 `127.0.0.1` 에만 바인딩되어 있는지(`bind-address`), ③ 다른 서버의 IP로 잘못 접속하는지 확인. 서버에서 `netstat -ano | findstr :3306` 으로 LISTEN 주소 확인.
</details>

<details>
<summary><b>Q3.</b> 외부 API 호출이 갑자기 모두 <code>UnknownHostException</code> 으로 실패한다.</summary>

**① DNS 단계** → 상대 서버보다 **우리 쪽 DNS** 문제일 가능성. `nslookup api도메인` 으로 조회되는지, 서버의 DNS 설정이 바뀌었는지, 도메인 오타가 없는지 확인.
</details>

<details>
<summary><b>Q4.</b> Postman으로 API를 호출하면 404가 나온다. 동료는 "서버가 죽었다"고 한다.</summary>

**④ HTTP 단계** → 404 응답을 **받았다는 것 자체가 서버가 살아 있다는 증거**. URL 경로, 컨텍스트 경로, HTTP 메서드, `@RequestMapping` 을 확인.
</details>

<details>
<summary><b>Q5.</b> 브라우저에서 <code>ERR_CONNECTION_REFUSED</code> 가 뜬다. 방금 전까지 잘 되던 로컬 개발 서버다.</summary>

**② TCP 거부** → 로컬 앱이 **죽었거나 재시작 중**. IDE 콘솔에서 앱이 예외로 종료되지 않았는지 확인, `netstat -ano | findstr :8080` 으로 LISTEN 확인.
</details>

## 7. 문의할 때 쓰는 템플릿

사수·인프라 담당자에게 물을 때 이렇게 정리하면 해결이 빨라집니다.

```
[접속 대상]   앱 서버(10.10.1.5) → DB 서버(db.example.internal:3306, TCP)
[증상]        Connect timed out (3초)
[확인한 것]   nslookup db.example.internal → 10.20.3.7 (DNS 정상)
             Test-NetConnection 10.20.3.7 -Port 3306 → 실패, 수십 초 걸림 (timeout으로 판단)
             같은 서버의 22번 포트는 연결 성공
[추정]        3306 포트 방화벽 미허용
```

> 🔐 사내 IP·도메인·계정이 담긴 내용은 **사내 채널로만** 공유하세요. 외부 커뮤니티나 AI 서비스에 그대로 붙여 넣지 않습니다.

---

## 체크리스트

- [ ] DNS → TCP → TLS → HTTP → 앱 진단 순서를 말할 수 있다
- [ ] UnknownHost / refused / timeout / 4xx / 5xx 를 직접 만들어 봤다
- [ ] refused와 timeout의 차이(RST vs 무응답)와 각각 의심할 것을 안다
- [ ] 스택트레이스에서 맨 아래 `Caused by` 를 찾아 실패 단계를 판단할 수 있다
- [ ] "ping이 안 되면 서버가 죽은 것"이 틀린 이유를 안다
