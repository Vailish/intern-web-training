# 04. TCP·UDP와 3-way handshake ⭐ 핵심

> 🎯 목표: **"TCP 연결"이 실제로 무엇인지** 패킷으로 직접 확인한다.
> 3-way handshake, 연결 종료, RST(연결 거부)를 Wireshark로 보고, **UDP는 왜 다르게 동작하는지** 체감한다.

- 스프링 로그의 `HikariPool-1 - Starting...` — 왜 DB 연결을 **미리 만들어 두는(pool)** 걸까?
- 면접 단골 질문: "TCP와 UDP의 차이는?", "3-way handshake를 설명하세요."

## 1. TCP vs UDP 한눈에

| | **TCP** | **UDP** |
|---|---|---|
| 연결 | 보내기 전에 **연결을 맺음** (3-way handshake) | 연결 없음. **바로 보냄** |
| 신뢰성 | 도착 확인(ACK), 빠지면 **재전송** | 확인 없음. 빠져도 모름 |
| 순서 | **보낸 순서대로** 전달 보장 | 순서 보장 없음 |
| 속도·부담 | 상대적으로 무거움 | 가볍고 빠름 |
| 데이터 단위 | 끊김 없는 **바이트 흐름(stream)** | 독립된 **꾸러미(datagram)** 하나하나 |
| 비유 | **등기 우편 + 전화 통화** | **전단지 뿌리기** |
| 주 용도 | 웹(HTTP), DB 접속, SSH, 이메일 | DNS, 실시간 영상·음성 통화, 게임 |

> 💡 **"UDP는 신뢰성이 없으니 나쁘다"가 아닙니다.** 화상 통화에서 0.5초 전 화면을 재전송받아 봐야 소용없습니다. **늦게 오는 것보다 빠뜨리는 게 나은** 곳에는 UDP가 맞습니다.
> 최신 **HTTP/3** 은 UDP 위에 신뢰성을 직접 구현한 **QUIC** 을 씁니다. "웹 = 무조건 TCP" 공식도 바뀌는 중입니다.

## 2. TCP가 신뢰성을 만드는 방법

| 장치 | 하는 일 |
|---|---|
| **순서 번호 (Seq)** | 보내는 바이트마다 번호를 붙임 → 받는 쪽이 순서대로 다시 조립 |
| **확인 응답 (ACK)** | "몇 번 바이트까지 잘 받았다"고 알려 줌 |
| **재전송** | 일정 시간 안에 ACK가 안 오면 다시 보냄 |
| **흐름 제어 (Window)** | 받는 쪽이 감당할 수 있는 만큼만 보내게 조절 |

### TCP 헤더의 플래그 (Wireshark Info 칸의 `[ ]` 안)

| 플래그 | 의미 |
|---|---|
| **SYN** | 연결 시작하자 (Synchronize, 순서 번호 맞추기) |
| **ACK** | 받았다 (확인 응답) |
| **PSH** | 데이터 들어 있음, 바로 앱에 전달해 줘 |
| **FIN** | 나는 더 보낼 게 없다 (정상 종료) |
| **RST** | 연결 강제 종료 / **거부** (Reset) |

## 3. 3-way handshake

```
   클라이언트                                   서버 (9000에서 LISTEN 중)
      │                                           │
      │ ──── ① SYN (Seq=x) ────────────────────▶  │   "연결하고 싶어. 내 시작 번호는 x"
      │                                           │
      │ ◀─── ② SYN + ACK (Seq=y, Ack=x+1) ─────── │   "좋아. 네 x 받았고, 내 시작 번호는 y"
      │                                           │
      │ ──── ③ ACK (Ack=y+1) ──────────────────▶  │   "네 y 받았어"
      │                                           │
      │ ═══════════ ESTABLISHED (연결 성립) ═══════ │   이제부터 데이터 전송
```

**왜 3번인가?** 양쪽 모두 **"내가 보낸 게 상대에게 가고, 상대가 보낸 게 나에게 온다"** 를 확인하고, 서로의 **시작 순서 번호**를 교환해야 하기 때문입니다.
2번이면 서버는 "내 SYN+ACK가 클라이언트에 도착했는지" 알 수 없습니다.

**코드와의 연결:**
- 클라이언트의 `socket.connect(...)` 한 줄 안에서 ①②③이 모두 일어납니다.
- 서버의 `server.accept()` 는 ③까지 끝나야 리턴됩니다.

## 4. 실습 A — 3-way handshake 캡처하기 ⭐

### 4-1. 실행
1. Wireshark: **`Adapter for loopback traffic capture`** 캡처 시작
2. 창 1:
   ```powershell
   cd 07_Network\샘플\socket-lab
   java "-Dfile.encoding=UTF-8" TcpEchoServer.java
   ```
3. 창 2:
   ```powershell
   cd 07_Network\샘플\socket-lab
   java "-Dfile.encoding=UTF-8" TcpClient.java
   ```
4. 창 2에 `hello` 입력 → `[echo] hello` 확인 → **Ctrl+Z 후 Enter** 로 종료
5. Wireshark 정지 → 필터 `tcp.port == 9000`

### 4-2. 실제 캡처 결과

```
No.  Time       Info
 1   0.000000   53437 → 9000 [SYN] Seq=0 Win=65535 Len=0 MSS=65495 ...          ┐
 2   0.000106   9000 → 53437 [SYN, ACK] Seq=0 Ack=1 Win=65535 Len=0 ...         ├ ① 3-way handshake (연결)
 3   0.000131   53437 → 9000 [ACK] Seq=1 Ack=1 Win=65280 Len=0                  ┘
 4   1.044334   53437 → 9000 [PSH, ACK] Seq=1 Ack=1 Win=65280 Len=7             ┐ ② "hello\r\n" (7바이트) 보냄
 5   1.044371   9000 → 53437 [ACK] Seq=1 Ack=8 Win=65280 Len=0                  ┘    서버: "8번 바이트 전까지 받았어"
 6   1.046526   9000 → 53437 [PSH, ACK] Seq=1 Ack=8 Win=65280 Len=14            ┐ ③ "[echo] hello\r\n" (14바이트) 응답
 7   1.046543   53437 → 9000 [ACK] Seq=8 Ack=15 Win=65280 Len=0                 ┘
 8   3.070630   53437 → 9000 [FIN, ACK] Seq=8 Ack=15 ...                        ┐
 9   3.070689   9000 → 53437 [ACK] Seq=15 Ack=9 ...                             ├ ④ 4-way 종료
10   3.071567   9000 → 53437 [FIN, ACK] Seq=15 Ack=9 ...                        │
11   3.071620   53437 → 9000 [ACK] Seq=9 Ack=16 ...                             ┘
```

**읽는 법:**
- `53437 → 9000`: 클라이언트(임시 포트 53437)가 서버(9000)로 보냄
- **1~3번 사이 시간이 0.0001초**: 내 PC 안(루프백)이라 매우 빠름. 실제 인터넷에서는 **왕복 시간(RTT)만큼** 걸립니다
- **Ack 값 = "다음에 받을 바이트 번호"**: 5번 `Ack=8` 은 "1~7번 바이트(hello\r\n)를 다 받았으니 다음은 8번" 이라는 뜻
- `Seq=0` 은 Wireshark가 보기 쉽게 바꾼 **상대 번호**입니다. 실제 시작 번호는 보안을 위해 **무작위**입니다

### 4-3. 그림으로 보기
**Statistics → Flow Graph** → `Limit to display filter` 체크, Flow type `TCP Flows`.
두 세로선(클라이언트, 서버) 사이에 위 11개 패킷이 **화살표**로 그려집니다. 위의 3-way handshake 그림과 비교해 보세요.

## 5. 연결 종료와 연결 상태

### 4-way 종료 (위 캡처의 8~11번)

```
 클라이언트 ── FIN ──▶ 서버     "나는 다 보냈어"
 클라이언트 ◀── ACK ── 서버     "알았어"         (서버는 아직 보낼 게 남았으면 더 보낼 수 있음)
 클라이언트 ◀── FIN ── 서버     "나도 다 보냈어"
 클라이언트 ── ACK ──▶ 서버     "알았어"
```

TCP는 **양방향 각각** 닫아야 해서 4단계입니다. `TcpClient.java` 의 `socket.shutdownOutput()` 이 바로 "내 쪽 방향만 닫기(FIN)" 입니다.

### 실습 B — 연결 상태 눈으로 보기

에코 서버를 켜 두고, 클라이언트가 **접속해 있는 동안** 다른 창에서:

```powershell
netstat -ano | findstr :9000
```
```
TCP    0.0.0.0:9000        0.0.0.0:0          LISTENING     60900    ← 서버: 대기 중
TCP    127.0.0.1:9000      127.0.0.1:49918    ESTABLISHED   60900    ← 서버 쪽에서 본 연결
TCP    127.0.0.1:49918     127.0.0.1:9000     ESTABLISHED   63388    ← 클라이언트 쪽에서 본 연결
```

클라이언트를 종료한 직후:
```
TCP    0.0.0.0:9000        0.0.0.0:0          LISTENING     60900
TCP    127.0.0.1:49918     127.0.0.1:9000     TIME_WAIT     0        ← 먼저 끊은 쪽(클라이언트)에 남음
```

| 상태 | 의미 | 실무에서 |
|---|---|---|
| `LISTENING` | 서버가 접속을 기다림 | 서버가 떠 있는지 확인 |
| `ESTABLISHED` | 연결 성립, 데이터 주고받는 중 | 현재 접속 수 |
| `TIME_WAIT` | **먼저 끊은 쪽**이 잠시 기다리는 상태 (늦게 도착한 패킷 처리용). OS 설정에 따라 수십 초~수 분 후 사라짐 | 짧은 연결을 **엄청 많이** 만들면 쌓여서 문제가 됨 → 연결 재사용이 필요한 이유 |
| `CLOSE_WAIT` | 상대는 끊었는데 **내 프로그램이 아직 close() 안 함** | 계속 쌓이면 **내 코드의 자원 누수** 신호 (close 누락) |

## 6. 실습 C — 연결 거부(RST) 보기

에코 서버를 **끈 상태**에서 Wireshark 캡처 후 클라이언트 실행:

```powershell
java "-Dfile.encoding=UTF-8" TcpClient.java
```
```
[연결 시도] localhost:9000 ...
[실패 단계] TCP
[의미]      상대 컴퓨터에는 닿았지만, 그 포트에서 기다리는 프로그램이 없습니다(RST 수신). ...
[원본 예외] java.net.ConnectException: Connection refused: no further information
```

캡처 결과 (필터 `tcp.port == 9000`):
```
12   53402 → 9000 [SYN] Seq=0 ...          ← 연결하자
13   9000 → 53402 [RST, ACK] Seq=1 Ack=1   ← 여기 아무도 없어! (OS가 대신 거절)
```

**`Connection refused` 의 정체 = SYN에 대한 RST 응답** 입니다.
상대 컴퓨터(OS)는 살아 있어서 대답은 했지만, 그 포트에 프로그램이 없다는 뜻입니다. → "서버 프로그램이 꺼져 있거나 포트 번호가 틀렸다"

> 💡 응답 자체가 **아예 없는** 경우(`Connect timed out`)와는 의미가 완전히 다릅니다. [06 문서](./06_에러로_원인찾기.md)에서 비교합니다.

## 7. 실습 D — UDP는 "던지고 끝" ⭐

### D-1. 서버를 끈 채로 보내기
Wireshark 루프백 캡처를 시작한 뒤 (정지 후 디스플레이 필터는 `udp.port == 9001`):

```powershell
java "-Dfile.encoding=UTF-8" UdpClient.java
```
`ping` 입력:
```
[전송 완료] "ping"  ← send() 는 에러 없이 끝났습니다
[답장 없음] 2000ms 동안 응답이 없습니다. 메시지가 도착했는지 UDP는 알려주지 않습니다.
```

**TCP라면 `connect()` 에서 바로 `Connection refused` 가 났을 상황**인데, UDP의 `send()` 는 **아무 에러 없이** 끝났습니다. 받을 사람이 있는지 확인하지 않기 때문입니다.

### D-2. 서버를 켜고 보내기
```powershell
# 창 1
java "-Dfile.encoding=UTF-8" UdpServer.java
```
```
[전송 완료] "ping"  ← send() 는 에러 없이 끝났습니다
[답장] [echo] ping
```

### D-3. 캡처 결과 비교 (실측, 필터 `udp.port == 9001`)
```
2    UDP    65025 → 9001 Len=4                               ← 서버 꺼짐: "ping" 4바이트를 그냥 보냄 (SYN 같은 사전 절차 없음)
3    ICMP   Destination unreachable (Port unreachable)       ← OS가 "그 포트 없음"이라고 알려 줌
9    UDP    63098 → 9001 Len=4                               ← 서버 켜짐: 보냄
10   UDP    9001 → 63098 Len=11                              ← 답장 "[echo] ping" 11바이트
```

> 💡 ICMP 오류 패킷 안에는 **원래 보냈던 UDP 헤더가 복사되어** 들어 있습니다. 그래서 `udp.port == 9001` 필터에 ICMP도 함께 걸립니다.
> 필터 없이 보면 다른 프로그램이 만든 ICMP 패킷이 섞여 보일 수 있습니다. 무시해도 됩니다.

**관찰 포인트:**
- UDP에는 **SYN, ACK, FIN이 전혀 없습니다.** 데이터 패킷 하나가 전부입니다.
- 서버가 꺼져 있을 때, 상대 OS가 **ICMP "Port unreachable"** 로 알려 주긴 했습니다. 하지만 우리 프로그램(연결 없는 UDP 소켓)은 그걸 **에러로 받지 못했습니다.**
  → UDP를 쓰는 프로그램은 "잘 갔는지"를 **스스로** 확인해야 합니다(답장 대기, 타임아웃, 재전송 등). 위 `UdpClient` 가 2초 타임아웃을 둔 이유입니다.

### TCP 코드 vs UDP 코드 비교

| | TCP (`TcpEchoServer.java`) | UDP (`UdpServer.java`) |
|---|---|---|
| 서버 준비 | `new ServerSocket(9000)` | `new DatagramSocket(9001)` |
| 접속 받기 | `server.accept()` ← **연결 단위** | 없음 |
| 데이터 받기 | 연결의 `InputStream` 에서 계속 읽기 (흐름) | `socket.receive(packet)` ← **패킷 단위** |
| 상대가 누구? | 연결이 기억함 | 패킷마다 적힌 주소를 보고 답장 |

## 8. 연결은 비싸다 — 커넥션 풀과 keep-alive

새 연결을 하나 만들 때마다 드는 비용:

```
 TCP 3-way handshake                        왕복 1번
 (+ HTTPS라면 TLS handshake)                 왕복 1~2번 더
 (+ DB라면 로그인·인증 절차)                  왕복 여러 번 더
 ───────────────────────────────────────────────────────
 → 그 다음에야 진짜 요청(SQL, HTTP) 전송
```

내 PC 안(루프백)에서는 왕복이 0.0001초라 차이를 못 느낍니다. 하지만 서버가 멀수록, 요청이 많을수록 이 비용이 쌓입니다. 또 짧은 연결을 수없이 만들면 `TIME_WAIT` 도 쌓입니다.

**그래서 "연결을 만들어 두고 재사용"합니다.**

| 기술 | 재사용 대상 | 어디서 봤나 |
|---|---|---|
| **커넥션 풀 (HikariCP)** | 앱 ↔ DB 연결 | 스프링 시작 로그 `HikariPool-1 - Start completed` |
| **HTTP keep-alive** | 브라우저 ↔ 웹서버 연결 | [05 문서](./05_HTTP는_TCP_위의_텍스트다.md)에서 curl로 확인 |

> 💡 HikariCP는 앱이 시작될 때 DB 연결을 여러 개 **미리** 맺어 둡니다. 요청이 오면 빌려 쓰고 반납합니다. 그래서 SQL 실행마다 handshake를 하지 않습니다.

## 9. 06_Deploy 다시 보기 — healthcheck는 왜 `-h 127.0.0.1` 이었나

`mysqladmin ping` 을 `-h` 없이 쓰면 TCP가 아니라 **유닉스 소켓(같은 컴퓨터 안의 프로세스끼리 쓰는 파일 형태의 통로)** 으로 접속합니다.
MySQL 초기화 중의 임시 서버는 **TCP 포트를 열지 않고 소켓만** 엽니다. 그래서 소켓 검사는 "살아있음"으로 나오지만, 앱(TCP로 접속)은 아직 접속할 수 없었습니다.
`-h 127.0.0.1` 을 주면 **TCP로 3-way handshake를 시도**하므로, 앱과 똑같은 조건으로 검사하게 됩니다.

## 10. 함정

| 오해·증상 | 실제 |
|---|---|
| "localhost 통신은 Wireshark에 안 잡혀요" | 이더넷이 아니라 **루프백 어댑터**를 골라야 함 |
| "TCP는 메시지 단위로 보낸다" | TCP는 **바이트 흐름**. 두 번 보낸 게 한 번에 붙어서 오거나, 한 번 보낸 게 나뉘어 올 수 있음. 그래서 HTTP는 `Content-Length` 나 줄바꿈으로 경계를 정함 |
| "UDP send()가 성공했으니 상대가 받았다" | 아니다. **보냈다**일 뿐 |
| `CLOSE_WAIT` 가 계속 늘어남 | 상대가 끊었는데 내 코드가 소켓·연결을 **close 안 함** (try-with-resources 확인) |
| 3-way handshake 질문에 "SYN, ACK, SYN-ACK" | 순서는 **SYN → SYN+ACK → ACK** |

---

## 체크리스트

- [ ] TCP와 UDP의 차이를 연결·신뢰성·순서·용도로 설명할 수 있다
- [ ] Wireshark에서 SYN → SYN+ACK → ACK 를 직접 찾았다
- [ ] Ack 번호가 "다음에 받을 바이트 번호"라는 것을 캡처로 확인했다
- [ ] `Connection refused` 가 RST 패킷이라는 것을 확인했다
- [ ] 서버가 꺼져 있어도 UDP send()는 에러가 나지 않는 것을 확인했다
- [ ] `LISTENING`, `ESTABLISHED`, `TIME_WAIT`, `CLOSE_WAIT` 의 의미를 안다
- [ ] 커넥션 풀과 keep-alive가 필요한 이유를 handshake 비용으로 설명할 수 있다
